memory

Write, revise, or remove what the agent carries between conversations.

What it does

The write side of Memory. Reading does not need a tool: every item in force is already in the prompt, listed and visible. This tool exists to change what is there.

ActionDoes
addStores one item. Requires text.
editReplaces an item's text. Requires id and text.
deleteRemoves an item. Requires id.
listReturns every item with its id, and the capacity used.

Why list exists when memory is already in the prompt

Two reasons, and neither is recall.

The prompt shows the items but not their identifiers, and edit and delete need one. Listing is how an item is addressed.

And the prompt is frozen between compactions, so after a write it is out of date — it shows memory as it stood, not as it stands. A question about what is remembered is therefore answered by listing, which the description says outright: this is the only record of what is remembered; list it to answer any question about what you know, rather than answering from the conversation.

When to write

There is no automatic trigger. No extraction pass runs at the end of a turn, nothing scans a transcript for facts, and nothing writes memory on the agent's behalf. The decision is the model's, and the only steering is one line of the persona:

- Write a memory item only for what stays true across conversations.
Deliberately discretionary. Recall is automatic so it cannot be forgotten; writing is not, because an agent that records everything it hears fills a capped store with the transient and then cannot fit what matters. The asymmetry is the design, and it is why the store is small enough to read at a glance.

Consolidation

Memory is capped. A write that would exceed the cap fails, and the failure carries everything already stored along with how much room there is. The agent is then expected to merge or delete in the same turn and retry.

Failing loudly is the point. Dropping the oldest item to make room produces an agent that quietly forgets and cannot tell you what it forgot.

This is also why edit and delete exist, and why they are exercised under pressure: they are reached from a failed add, in a turn that was trying to do something else.

Acceptance criteria

  • add stores one item and returns its identifier.
  • list returns every item with its identifier, and the capacity used against the capacity available.
  • edit replaces the text of the named item and nothing else.
  • delete removes the named item and nothing else.
  • edit or delete naming an unknown identifier fails and says so.
  • add with empty text is refused.
  • A write that would exceed the capacity fails, states what is stored and how much room there is, and stores nothing.
  • The store is not scoped to a session: an item written in one conversation is listed in every other.
  • Every action writes a visible transcript entry naming what it did.
  • Eval cases cover all four actions, including consolidation reached from a failed write.
