web_search

Search the web and return titles, URLs, and snippets.

What it does

Puts the query to a search API over HTTPS with the agent's own key, and returns what it answered. There is no browser in this tool any more, and no results page to read (ADR-059): a search engine's own page is the one surface that will not be read by an automated client, and the engines that decline say so while the one that does not answers with results belonging to somebody else's query.

ParameterMeaning
queryThe search terms. Required.
limitMaximum results. Optional; ten by default. It is what the API is asked for, not a cut made afterwards — fetching ten to show three costs three times as much for the same three.

The key is the agent's, not a conversation's

Every other credential reaches a tool because the conversation it runs in was granted it by name (ADR-045). Search is not like that. A grant is for a credential that belongs to a piece of work — this repository, this forge, this conversation — and search belongs to the agent the way the model does: a conversation that had to be granted it would be a conversation that cannot look anything up until somebody notices.

So the tool's manifest names TAVILY_API_KEY, and the registry gives it that variable from the agent's own environment on every call. A manifest that names a variable is the only way a tool receives one outside a grant, it is declared per tool for the reason read paths are, and the Tools screen prints the names on that tool's card — the name, never the value. bash declares nothing, so the search key is not in the environment of the tool that runs commands the model wrote.

Where the key is not set the tool fails saying which variable is missing and where it goes. That failure is the operator's to fix and a model cannot fix it, so the message says so rather than inviting a retry.

Outcomes, told apart

OutcomeAnswer
Results foundTitle, URL, and snippet for each, numbered.
The API had no matchesSays there were no results for the query.
The API refused — a rejected key, a spent allowance, a rate limitFails, carrying the status and what the API said about it.
No key configuredFails, naming TAVILY_API_KEY and where the operator sets it.

Conflating the first two is the failure that matters, and it is why a refusal is never reported as an absence: no results invites the agent to conclude the thing does not exist, where a refusal means it did not get to look. A status code alone does not tell a rejected key from a spent allowance, so whatever the API said about the refusal is carried through — those ask different things of the operator.

A result without a URL is dropped rather than shown. The model's next move is to fetch one, and a hit it cannot follow is a line of text pretending to be a source.

Acceptance criteria

  • A query with results returns a title, a URL, and a snippet for each.
  • The limit is what the API is asked for, and defaults to ten.
  • The key travels in the request and comes from the agent's environment, not from a session's grants.
  • A tool that does not name the key in its manifest never receives it, bash included.
  • A query with no matches says so, naming the query, and is not a failure.
  • A refusal by the API fails and carries what the API said, and is never reported as an absence of results.
  • A search with no key configured fails, names the variable, and says where it is set.
  • An empty query is refused.
