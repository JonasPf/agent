web_search

Search the web and return titles, URLs, and snippets.

What it does

Puts the query to a search engine in a headless browser and reads the results out of the rendered page. The browser introduces itself as an ordinary Chrome at the installed version, without the Headless in chromium's own user agent (ADR-046).

ParameterMeaning
queryThe search terms. Required.
limitMaximum results. Optional; ten by default.

Why a browser and not a request

A results page is assembled by scripts. Fetching its HTML returns a shell with no results in it, so unlike web_browse there is no useful unrendered path here: without a browser this tool cannot do its job, and says so rather than returning an empty list that reads like a query with no matches.

Three outcomes, told apart

OutcomeAnswer
Results foundTitle, URL, and snippet for each, up to the limit.
The engine served a page with no resultsSays there were no results for the query.
The engine declined — a rate limit, a challenge, a blockFails, names the refusal, and suggests fetching a specific page instead.
The engine answered with somebody else's resultsFails, says the results bore no relation to the query, and does not show them.

The middle and the last look identical in the parsed output — both yield nothing — and conflating them is the failure that matters. "No results" invites the agent to conclude the thing does not exist; a refusal means it did not get to look. The rendered text is inspected for the signature of a refusal precisely so the two can be told apart.

An answer that is not an answer

A refusal is the honest failure: the engine says it will not serve an automated query, and the tool reports it. Bing does something else. It answers — a page carrying the query in its own title, ten well-formed organic results on it, and every one of them about something unrelated, a different set on each request: gift card retailers, hospital listings, Manhattan attractions, in reply to a query about OCR binaries. There is no challenge anywhere on the page, so nothing in the parsed output tells it apart from a real answer, and the model reasons from it as though it were one. That is worse than a refusal and worse than an empty page, because both of those are legible.

So the results are read against the query before they are shown: across every result on the page, does any word of the query appear in any title, URL, or snippet. The test is the weakest one that catches this — a genuine result set clears it on its first hit, a page of filler clears it on none. Where a query is nothing but common words there is nothing to look for, and the tool judges nothing rather than guessing. It is not a relevance ranking and it never drops an individual result: either the page is an answer to the query or it is not.

Acceptance criteria

  • A query with results returns a title, a URL, and a snippet for each.
  • The number of results respects the limit, and defaults to ten.
  • A query with no matches says so, naming the query.
  • A refusal by the search engine fails, names what happened, and is never reported as an absence of results.
  • A page of results bearing no relation to the query fails rather than returning them, and says that is what happened.
  • One result mentioning one word of the query, anywhere in it, is enough for the page to count as an answer.
  • A query made only of common words never triggers that check.
  • An empty query is refused.
  • Where no browser is available the tool fails and says why, rather than returning an empty result set.
