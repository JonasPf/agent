web_browse

Fetch a URL and return the page's text.

What it does

Loads the URL and returns what a person would read. Where a headless browser is installed, the page is rendered: scripts run and the DOM settles first, so a page assembled on the client reads the same as it would in a window. A body that is not HTML — JSON, plain text — comes back verbatim rather than being stripped of markup it does not have.

ParameterMeaning
urlThe address to fetch. Required.

One path, and it renders

There is no second way through. Every page this tool returns has been run in a browser and read from the settled DOM.

It used to have a fallback: with no browser installed it fetched the bytes over plain HTTP, and a page that assembles itself on the client came back as the shell it ships as. The trouble was that the caller could not tell which had happened — a thin page and a page whose scripts never ran read identically. The browser is now installed in the image at a fixed path (ADR-044), so its absence is a broken image and is reported as one.

A plain HTTP fetch is a reasonable thing to want, and cheaper than this. When it is wanted it should be a tool of its own, named for what it does, chosen by the model on purpose — not a silent substitution made on its behalf.

The browser says what it is, and no more. The request carries the user agent of an ordinary Chrome at the installed version. Headless chromium's own string differs only in the word HeadlessChrome, which says nothing a window would not and is the first thing a site that turns away automation reads (ADR-046). Nothing else is altered: there is no cookie jar, no fingerprint masking, no retry through another route, and no bot check is answered or evaded. A tool that worked around refusals would be a tool whose behaviour the operator could not predict from what it says.

A bot check is not the page

To a browser, a bot check is a page like any other: it loads, its scripts run, and it has text. Returned as the answer, Just a moment… Performing security verification reads as what a product page says. So the tool fails instead, naming whose check it met — Cloudflare, DataDome, or HUMAN — and saying that a browser started any other way meets the same check.

A check is recognised by a vendor's marker on a page with almost nothing else to say. The marker alone is not enough: the same vendors put their scripts on pages they serve normally, and a readable page reported as unreadable is the costlier mistake, because the model stops looking.

Limits

The response body is read up to two megabytes, and the text returned is capped at forty thousand characters. A page longer than that is cut, and the cut is reported.

Acceptance criteria

  • An HTML page returns its readable text, without markup.
  • A page whose content is assembled by scripts returns that content where a browser is available.
  • A non-HTML body is returned verbatim.
  • Where no browser is available the tool fails saying so, rather than fetching the bytes instead: an image without a browser is broken, not degraded.
  • Text beyond the cap is truncated and the result says it was truncated.
  • A response body beyond the byte limit is read no further.
  • A refused or failed request reports the status and does not retry by another route.
  • The request carries an ordinary Chrome user agent at the installed version, without Headless.
  • A page that is a vendor's bot check fails naming the vendor, and is not returned as the page's text.
  • An empty URL is refused.
