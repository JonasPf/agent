Sessions

A session is a conversation. It is the only container for model interaction.

There is one kind of session. Scheduled work runs inside an existing conversation rather than in a private one of its own, so a session is always something a person started and can read.

Acceptance criteria

  • Every session appears in the session list; none are hidden by kind or origin.
  • A session receives a title within one turn of its first user message.
  • A session's model, tools, and skills cannot be changed once the session exists.
  • The configuration of one session does not affect any other.
  • The system prompt as sent is retrievable for any session that has taken a turn.

Position zero

Every session opens with a prompt entry: the complete system prompt as sent, split into sections you can expand. Persona, memory, the skills index, and the full tool definitions are all there.

It is written when the session is created, from the configuration chosen before it existed. A session therefore has a prompt from its first moment, and nothing reading position zero has to allow for its absence.

┌─ prompt · 4,180 tokens                        ─┐
│  persona            310 tokens        expand   │
│  memory · 12 items  480 tokens   edit expand   │
│  skills · 6         190 tokens        expand   │
│  tools · 12       3,200 tokens        expand   │
└────────────────────────────────────────────────┘

Nothing that shapes the agent's behaviour is anywhere else. Scrolling to the top of a conversation shows exactly what it was told, including every tool definition it can see.

The entry is a record of what was sent, so it is not sent again and costs nothing. Sections are collapsed by default, because tool definitions are long and are usually not what you came to read.

The prompt does not change

Position zero is not a snapshot that later drifts. It is the prompt, for the whole life of the session. Nothing that shapes behaviour can move underneath a conversation, because everything that shapes it is chosen before the conversation starts.

Writing a memory is the one thing that changes what a later session is told, and it takes effect there rather than here: the entry records it, and the next session's prompt carries it.

Acceptance criteria

  • Every session's first entry, once it has taken a turn, is the system prompt as sent, sectioned and expandable.
  • Tool definitions are shown in full, exactly as the model receives them.
  • Each section shows its token count, and the entry shows the total.
  • The memory section is editable in place; no other section is.
  • The prompt entry is not sent to the model.
  • A session that has not taken a turn has no prompt entry, and its configuration is still editable.
  • The prompt a session is sent is identical on its first turn and its last.

Configuration

A session's model, its tools, and its skills are one thing: the configuration. It is chosen before the conversation starts and fixed from the session's first turn.

So the prompt carries exactly what the session can use. The tool definitions in position zero are the tools that are callable; the skills index lists the skills that can be read. There is no second, smaller set hiding behind a larger one.

Changing it is continuing. To run on a different model, or with a different set of tools, you rotate: the conversation continues in a new session under the new configuration, carrying its summary and recent turns across. There is no other way to change it, and no need for one.

Why fixed

The alternative is to make configuration mutable and pay for it somewhere. Rewriting the prompt on every change invalidates the cached prefix, worst on exactly the long conversations where a change is most tempting. Keeping the prompt fixed while varying what is allowed avoids that, but buys it with a permanent gap between what the prompt says and what is true: every definition present, some of them refusals waiting to happen, an appended entry to explain the difference, and a dispatch check to enforce it.

Rotation removes the dilemma rather than picking a side. A change of configuration is a change of prompt, a change of prompt is a new session, and a new session is a thing the system already does well: the summary and the recent turns come across, the jobs come across, and the cached prefix of the old session was never invalidated because it was never touched.

What that removes, concretely: the enabled set no longer diverges from the prompt, no entry has to announce a change mid-conversation, no call has to be refused for being disabled, a skill outside the session's set is simply not a skill it has, and a job that runs days later runs under the same configuration it was created under.

What is still mutable. Title, status, and the rolling summary. None of them appear in the prompt, so none of them can invalidate it. Model, tools, and skills never do.

A new session inherits the configuration of the most recently used one, and a fork inherits its predecessor's, so the common case is a screen you confirm without changing anything. Both are the same screen, reached the same way, and both are answered before the session exists.

Acceptance criteria

  • The prompt defines exactly the session's enabled tools, and indexes exactly its enabled skills.
  • A session's configuration is chosen before it is created and cannot be changed afterwards.
  • A request to change a session's model, tools, or skills is refused, and names rotation as the way.
  • Every session has a prompt entry from the moment it exists.
  • Rotating accepts a configuration; anything not given is inherited from the predecessor.
  • A rotation that changes the configuration names what changed, in both sessions' transcripts.
  • A new session inherits the configuration of the most recently used session.
  • Nothing that can be changed mid-session appears in the system prompt.

Transcript entries

A transcript holds two kinds of entry. The distinction is what makes a conversation both complete and affordable.

TypeWritten byShown to userSent to model
messageuser, assistant, tool resultyesyes
eventsystem: job checks, rotations, failuresyesno

What an event is for

An event exists only where nothing else records what happened. A check that exits non-zero costs no model call and produces no message, so without an event a job that polled for six hours leaves no trace at all — and a job that died on its first tick would look identical. That difference is the whole justification, and it is the test every event has to pass.

EventRecords
job_checkA check ran and what it decided. Nothing else records a tick that did not fire.
job_errorA job failed. Failing is not something the model says.
errorA turn failed.
rotationThe conversation continued in a new session.
carried_overWhich turns arrived from a predecessor.

Nothing else is an event. An action whose result already appears in the transcript — a tool call answering for itself — is not written twice, and one whose result is a row on another screen is recorded by that row. Creating a job, adding a tool, updating the summary, and uploading a file are all of these, so none of them writes an entry.

Cheapness is not a reason. An event costs no tokens, which is an argument for keeping one that carries information and no argument at all for keeping one that repeats a line already on the screen. A transcript is read by a person; its budget is attention, not tokens.

Acceptance criteria

  • A check job that never fires still leaves one entry per tick.
  • Creating a job, registering a tool, updating a summary, and uploading a file write no transcript entry.
  • Every event kind that exists records something no other entry and no other screen records.
  • The prompt is its own entry type, not an event.
  • A wake is attributed to its job, named in the speaker itself. The operator is never shown as the author of a turn they did not type.
  • The job attribution appears once, on the wake, and not on the replies it produced.
  • Every message carries the time it was written, with the date shown once it is not today's.

Projection

What is stored and what is sent are different. A single projection step converts a transcript into the message list for a model call.

flowchart LR T["Transcript
(JSONL, complete)"] --> P{{"Projection"}} P --> M["Messages
(sent to model)"] P -.->|"drop"| E["events"] P -.->|"collapse"| C["repeated job ticks
→ one line + count"] P -.->|"mark"| W["job wake
→ names its job, operator absent"]

The projection applies five rules and nothing else:

  1. Entries of type event are dropped.
  2. Consecutive job_check events sharing a job_id and a status collapse into a single line carrying the repetition count and the elapsed span. Only a wake with a check produces these; a wake that acts produces messages, which are never collapsed.
  3. A user entry carrying a job_id is a wake, and is marked as one: it names the job, says how late it ran when that is more than a minute, and states that the operator is not present. A user entry without one is what the operator typed, and is left alone.
  4. A failed run projects as one line saying the turn above produced no reply, and carrying the failure. Every other event is dropped.
  5. Everything else passes through unchanged.

The turn's own user message goes through the projection too, rather than being assembled separately. Two ways of putting a user turn on the wire is two rules to keep in step, and when they drifted the wake marker was the thing that went missing.

A failure is the one event the model is shown, because a turn that failed left its input in the transcript with nothing after it. Two wakes of one job then read as the same instruction given twice, and the model answers it twice — one reminder reaching the operator as two. The line between them is what makes the first one legible as a run that died.

Collapsing preserves the count deliberately. "Checked forty-seven times over three hours with no change" supports a conclusion that "checked once" does not.

Acceptance criteria

  • Projection is a pure function of a transcript; running it twice on the same input gives the same output.
  • A user entry carrying a job id reaches the model marked as a wake, naming the job and saying the operator is not present.
  • A wake that ran more than a minute after it was due says how late it is and when it was due; a punctual one says nothing about the clock.
  • A user entry with no job id reaches the model exactly as it was typed.
  • No event entry appears in a model request, except a failure, which appears as one derived line.
  • A wake whose run failed is followed in the request by a line saying it produced no reply, so an unanswered instruction is never mistaken for a repeated one.
  • Five consecutive ticks with identical status project to one line stating five occurrences and the time span.
  • Only the trailing run of ticks is collapsed; a run followed by a later user message is never re-collapsed.
  • Collapsing never removes an entry from the stored transcript.
Why only the trailing run. Caching keys on a stable prefix. Rewriting the middle of a conversation invalidates everything after it. Collapsing only the tail shortens the part that is cheapest to resend and leaves the cached prefix untouched.

Rolling summary

Every session maintains a summary of itself, updated as it grows rather than assembled under pressure when the context fills.

The update is incremental: the summariser sees the previous summary and the messages added since, never the whole conversation. That is what keeps it cheap — the cost of an update depends on how much was added, not on how long the conversation has become.

It runs on the session's model, like everything else. One model is used throughout the system.

The summary is not part of its own session's prompt. Putting it there would rewrite the prefix on every update and invalidate the cache — the thing the whole design protects. It lives beside the session and is used only to seed another one.

Growth is measured on the messages as the model would receive them, not on their text. A session that spends its context on tool results — fetched pages, command output — carries almost nothing in the text of its own turns, and measuring text alone would let it rotate on tokens the summariser never counted, handing its successor an empty summary.

Acceptance criteria

  • The summary updates after roughly every four thousand tokens of growth.
  • An update reads only the previous summary and the messages since it, not the full transcript.
  • Summaries run on the session's model; no part of the system selects a model of its own.
  • The summary is visible and editable in the interface.
  • Updating the summary does not alter the session's prompt or invalidate its cached prefix.
  • A session that has never grown past the threshold has no summary and needs none.
  • Growth counts the projected messages, so a session growing only in tool results is still summarised.

Rotation

When a conversation passes a size threshold, it does not compact. It rotates: a new session opens, seeded with the summary, and the old one is archived intact.

The threshold is chosen for cost, not for the model's context limit. Those limits now reach a million tokens, far past the point where every call becomes expensive: input is charged per token, so a session that has grown to eighty thousand tokens costs four times one at twenty thousand, on every single call and whether or not it is cached. The default threshold is forty thousand projected tokens.

The summary alone is not enough to continue with. It says what the conversation is about, but the last few exchanges are exactly what compresses worst and matters most — three options the agent just offered, a question waiting to be answered, the file it was working on.

The predecessor's summary reaches the successor in its system prompt, as a carried_summary section. It is not a message: the user role means the operator is speaking, and the summary is not something they said. It is frozen when the successor is created — read before the prompt entry is written, and never rewritten afterwards — so it sits inside the cached prefix rather than breaking it, and the prompt the transcript records is the prompt that is sent. The successor's own rolling summary starts empty and is a separate field; the two never overwrite each other. The text is also written into the carried_over event, which the projection drops, so the append-only transcript records what the successor started from at no cost in tokens.

So a successor opens with the summary in its prompt and then as many of the most recent turns as fit in a token budget, oldest of those first. The budget is a size, not a message count, because messages range from a line to a whole file. Turns are copied whole: never half of an exchange, and never an assistant message separated from the tool results it produced.

The successor therefore starts at a known size — around six thousand tokens by default, against a rotation threshold of forty thousand — so it has room to grow before rotating again.

Identity across a rotation

A successor gets a new identifier. Reusing the predecessor's would mean an identifier that silently starts addressing different content, which is the one thing the design does not do anywhere else.

It would not avoid the problem either. The predecessor still exists and is still readable, so it needs an identifier of its own — and if the archive is the one that gets renamed, then every reference that pointed at it now resolves to something else. Something has to be renamed; it should be the thing nobody has a link to yet.

References are kept working by following the chain forward instead:

  • Jobs move to the successor when their session rotates.
  • Opening an archived session from a link follows continued_by to the live session, and says that it did.

This is the same operation as forking a session or resuming an old one. All three create a session whose continued_from names its predecessor, seeded with that predecessor's summary and recent turns. Rotation is automatic; the other two are asked for.

Why rotate rather than compact. Compaction rewrites the prefix at the worst possible moment, pays for a large summarisation turn under pressure, and leaves a conversation that is half transcript and half summary. Rotation costs nothing at the moment it happens, because the summary already exists, and the successor starts with a clean prefix that caches from its first turn.

Exact history is not lost: the predecessor's transcript stays on disk and remains searchable, so something said before a rotation is still retrievable by search.

Acceptance criteria

  • Passing the size threshold opens a successor session seeded with the summary and archives the predecessor.
  • The carried summary reaches the successor's model in the system prompt, not as a user message.
  • The carried summary is fixed for the successor's life and recorded in its carried_over event.
  • The successor also carries the most recent complete turns that fit a token budget, defaulting to five thousand.
  • A turn is carried whole or not at all, including any tool results it produced.
  • Carried turns are marked as coming from the predecessor and link back to their place in it.
  • A successor has an identifier of its own; no identifier ever comes to address different content.
  • Following continued_by from any session in a chain reaches the live one.
  • A link to an archived session resolves to the live session and reports the redirection.
  • The threshold is configurable, defaults to forty thousand projected tokens, and is always below the model's context limit.
  • Rotation happens only between turns, never during one.
  • The successor records its predecessor, and the interface links both ways.
  • Jobs attached to the predecessor move to the successor.
  • Forking and resuming use the same mechanism and are available from the interface.
  • Search finds content in archived predecessors.

Ordering

A session executes strictly one turn at a time. User messages and job runs enter the same queue for that session, and a job never interleaves with a turn in progress.

Acceptance criteria

  • Two turns never run concurrently in one session.
  • A job firing while a user turn is running waits and then runs.
  • A user message queued behind a job run is not reordered ahead of it or dropped.
  • Different sessions run concurrently without blocking each other.

Working directory

Each session owns a directory. Its tools run in it, its uploads land in it, and a relative path in a tool call means a file in it. Nothing is shared: two conversations writing notes.txt write two files.

A continuation carries files as well as words. Rotation, fork, and resume all start the successor from a copy of the predecessor's directory, so a conversation continues with the files it was working on, and neither session's later writes reach the other.

Acceptance criteria

  • A session's tools run in that session's directory, and no other session's tools can read it.
  • A file uploaded to a session is written there, and its tools see it immediately.
  • A continuation starts from a copy of its predecessor's directory; writes after that are independent.
  • The files a session holds are listed, downloaded, and deleted through the API.
  • A path that would leave the session's directory is refused.
  • Deleting a session deletes its directory.
  • A session reports what it occupies on disk: its transcript and its working directory.

Export and import

A session travels as one zip: meta.json, transcript.jsonl, jobs.json, job_runs.json, and the working directory under files/. The archive mirrors what is on disk, so it can be read without this program.

An import restores the session under the identifier it already carries: a restored conversation is the one it was rather than a copy of it, and its links, its jobs, and its files all still name it. An identifier already present is therefore a conflict and the import is refused rather than merged.

Memory is not in it. Memory is durable across every conversation rather than owned by one, so an archive that carried it would change what every later session is told, silently, on import. An export is a session and nothing wider.

Acceptance criteria

  • An export carries the session's metadata, transcript, jobs, their run logs, and working directory.
  • An import restores all of them, in whichever agent reads the archive.
  • An imported transcript is searchable and its jobs run.
  • An import naming a session already present is refused, and says which.
  • An archive that is not a session is refused and nothing is altered.
  • Memory is not exported.

Search

A session_search tool queries a full-text index over all transcript entries across all sessions, so the agent can retrieve something said in a conversation that is no longer open.

Acceptance criteria

  • Search returns matches from sessions other than the current one.
  • Each result identifies its session and position so the user can open it.
  • Event entries are searchable.
  • The index is rebuildable from transcripts alone.
