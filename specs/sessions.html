Sessions

A session is a conversation. It is the only container for model interaction.

There is one kind of session. Scheduled work runs inside an existing conversation rather than in a private one of its own, so a session is always something a person started and can read.

Identity

FieldMeaning
idULID. Sortable by creation time, short enough to paste. It addresses the same conversation for as long as the conversation exists.
titleGenerated from the first user message. Editable.
modelThe model this conversation runs on. Fixed for the session's life.
statusactive or archived. Archiving is something a person does when they are finished; nothing archives a session automatically.

Acceptance criteria

  • Every session appears in the session list; none are hidden by kind or origin.
  • A session receives a title within one turn of its first user message.
  • A session's model, tools, and skills cannot be changed once the session exists.
  • The configuration of one session does not affect any other.
  • The system prompt as sent is retrievable for any session that has taken a turn.
  • A session identifier addresses the same conversation for that conversation's whole life.

Position zero

Every session opens with a prompt entry: the complete system prompt as sent, split into sections you can expand. Persona, memory, the skills index, and the full tool definitions are all there.

It is written when the session is created, from the configuration chosen before it existed. A session therefore has a prompt from its first moment, and nothing reading position zero has to allow for its absence.

┌─ prompt · 4,180 tokens                        ─┐
│  persona            310 tokens        expand   │
│  memory · 12 items  480 tokens   edit expand   │
│  skills · 6         190 tokens        expand   │
│  tools · 12       3,200 tokens        expand   │
└────────────────────────────────────────────────┘

Nothing that shapes the agent's behaviour is anywhere else. Scrolling to the top of a conversation shows exactly what it was told, including every tool definition it can see.

The entry is a record of what was sent, so it is not sent again and costs nothing. Sections are collapsed by default, because tool definitions are long and are usually not what you came to read.

The prompt changes only at a compaction

Between compactions the prompt is frozen. Nothing that shapes behaviour moves underneath a conversation mid-flight, because everything that shapes it is chosen before the conversation starts and every later change waits for a moment that is announced.

That moment is a compaction, and it is the only one. A compaction rewrites the head of the message list and therefore discards the cached prefix already — so re-photographing the prompt at the same instant costs nothing that was not already being spent. At any other moment it would cost a full cache write.

A compaction appends a new prompt entry rather than editing the old one. The transcript is append-only, so every prompt a session has ever been sent stays readable in the position it was sent from. The rule for what is current is simply the newest one.

Memory is why this exists. Memory written during a conversation has to reach that conversation eventually, or the agent writes things it can never read. A compaction is where it lands. See Memory.

Acceptance criteria

  • Every session's first entry, once it has taken a turn, is the system prompt as sent, sectioned and expandable.
  • Tool definitions are shown in full, exactly as the model receives them.
  • Each section shows its token count, and the entry shows the total.
  • The memory section is editable in place; no other section is.
  • A prompt entry is not sent to the model as a message; the newest one is sent as the system message.
  • A session that has not taken a turn has no prompt entry, and its configuration is still editable.
  • A session that has never compacted has exactly one prompt entry.
  • The prompt a session is sent is identical on every turn between two compactions.
  • A prompt entry written by a compaction records which entry superseded which.

Configuration

A session's model, its tools, and its skills are one thing: the configuration. It is chosen before the conversation starts and fixed for the session's entire life.

So the prompt carries exactly what the session can use. The tool definitions in position zero are the tools that are callable; the skills index lists the skills that can be read. There is no second, smaller set hiding behind a larger one.

Changing it is forking. To run on a different model, or with a different set of tools, you fork: the conversation is copied into a new session under the new configuration, and the original stays where it is. There is no other way to change it, and no need for one.

Why fixed

The alternative is to make configuration mutable and pay for it somewhere. Rewriting the prompt on every change invalidates the cached prefix, worst on exactly the long conversations where a change is most tempting. Keeping the prompt fixed while varying what is allowed avoids that, but buys it with a permanent gap between what the prompt says and what is true: every definition present, some of them refusals waiting to happen, an appended entry to explain the difference, and a dispatch check to enforce it.

Forking removes the dilemma rather than picking a side. A change of configuration is a change of prompt, a change of prompt is a new session, and a new session is a thing the system already does well: the whole conversation comes across, the files come across, and nothing about the original is touched.

What that removes, concretely: the enabled set no longer diverges from the prompt, no entry has to announce a change mid-conversation, no call has to be refused for being disabled, a skill outside the session's set is simply not a skill it has, and a job that runs days later runs under the same configuration it was created under.

What is still mutable. Title and status. Neither appears in the prompt. Model, tools, and skills never change at all.

A new session inherits the configuration of the most recently used one, and a fork inherits its origin's, so the common case is a screen you confirm without changing anything. Both are the same screen, reached the same way, and both are answered before the session exists.

Acceptance criteria

  • The prompt defines exactly the session's enabled tools, and indexes exactly its enabled skills.
  • A session's configuration is chosen before it is created and cannot be changed afterwards.
  • A request to change a session's model, tools, or skills is refused, and names forking as the way.
  • Every session has a prompt entry from the moment it exists.
  • Forking accepts a configuration; anything not given is inherited from the origin.
  • A fork that changes the configuration names what changed, in both sessions' transcripts.
  • A new session inherits the configuration of the most recently used session.
  • Nothing that can be changed mid-session appears in the system prompt.

Transcript entries

A transcript holds four kinds of entry. The distinction is what makes a conversation both complete and affordable.

TypeWritten byShown to userSent to model
messageuser, assistant, tool resultyesyes
eventsystem: job checks, forks, failuresyesno
promptsystem, at creation and at each compactionyesas the system message, newest only
compactionsystem, at the size thresholdyesyes, in place of what it covers

A compaction is its own type rather than an event because an event is never sent to the model and a compaction always is. It is not a message either: no one said it, and it stands for entries rather than adding to them.

What an event is for

An event exists only where nothing else records what happened. A check that exits non-zero costs no model call and produces no message, so without an event a job that polled for six hours leaves no trace at all — and a job that died on its first tick would look identical. That difference is the whole justification, and it is the test every event has to pass.

EventRecords
job_checkA check ran and what it decided. Nothing else records a tick that did not fire.
job_errorA job failed. Failing is not something the model says.
errorA turn failed, or a compaction failed and the conversation continued uncompacted.
forkThis conversation was copied into a new session. Written in the origin, which is otherwise unchanged and would show no trace.
forked_fromThis session began as a copy of another, at a named point in it.

Nothing else is an event. An action whose result already appears in the transcript — a tool call answering for itself — is not written twice, and one whose result is a row on another screen is recorded by that row. Creating a job, adding a tool, and uploading a file are all of these, so none of them writes an entry. Compacting writes entries, but they are not events: a prompt and a compaction, both of which the model is sent.

Cheapness is not a reason. An event costs no tokens, which is an argument for keeping one that carries information and no argument at all for keeping one that repeats a line already on the screen. A transcript is read by a person; its budget is attention, not tokens.

Acceptance criteria

  • A check job that never fires still leaves one entry per tick.
  • Creating a job, registering a tool, and uploading a file write no transcript entry.
  • Every event kind that exists records something no other entry and no other screen records.
  • The prompt and the compaction are their own entry types, not events.
  • A wake is attributed to its job, named in the speaker itself. The operator is never shown as the author of a turn they did not type.
  • The job attribution appears once, on the wake, and not on the replies it produced.
  • Every message carries the time it was written, with the date shown once it is not today's.

Projection

What is stored and what is sent are different. A single projection step converts a transcript into the message list for a model call.

flowchart LR T["Transcript
(JSONL, complete)"] --> P{{"Projection"}} P --> M["Messages
(sent to model)"] P -.->|"drop"| E["events"] P -.->|"fold"| F["entries a compaction covers
→ its summary, once"] P -.->|"collapse"| C["repeated job ticks
→ one line + count"] P -.->|"mark"| W["job wake
→ names its job, operator absent"]

The projection applies seven rules and nothing else:

  1. The newest prompt entry becomes the system message. Every earlier one is dropped.
  2. Only the newest compaction entry is sent, as an assistant message, in the position it was written. Every earlier one is dropped.
  3. Every entry at or before that compaction's covers_through is dropped, whatever its type.
  4. Entries of type event are dropped.
  5. Consecutive job_check events sharing a job_id and a status collapse into a single line carrying the repetition count and the elapsed span. Only a wake with a check produces these; a wake that acts produces messages, which are never collapsed.
  6. A user entry carrying a job_id is a wake, and is marked as one: it names the job, says how late it ran when that is more than a minute, and states that the operator is not present. A user entry without one is what the operator typed, and is left alone.
  7. A failed run projects as one line saying the turn above produced no reply, and carrying the failure. Everything else passes through unchanged.

Rules 1 to 3 are what make a compaction a projection rule rather than a rewrite. Nothing is edited and nothing is removed: the transcript grows by two entries, and the projection stops sending what they stand for.

A compaction is projected as an assistant message because the alternatives are worse. The user role means the operator is speaking, and the operator did not say it. The system message is the frozen prompt, and putting a changing summary there would break the one block that must not change between compactions. An assistant message is also simply true: the summary is the agent's own account of its own conversation, written by its own model.

The turn's own user message goes through the projection too, rather than being assembled separately. Two ways of putting a user turn on the wire is two rules to keep in step, and when they drifted the wake marker was the thing that went missing.

A failure is the one event the model is shown, because a turn that failed left its input in the transcript with nothing after it. Two wakes of one job then read as the same instruction given twice, and the model answers it twice — one reminder reaching the operator as two. The line between them is what makes the first one legible as a run that died.

Collapsing preserves the count deliberately. "Checked forty-seven times over three hours with no change" supports a conclusion that "checked once" does not.

Acceptance criteria

  • Projection is a pure function of a transcript; running it twice on the same input gives the same output.
  • The system message sent is the newest prompt entry; earlier prompt entries appear nowhere in the request.
  • A transcript with a compaction projects to that compaction's text followed by the entries after it, and nothing before it.
  • A transcript with two compactions sends only the newer one.
  • A compaction reaches the model as an assistant message, not as a user or system message.
  • A user entry carrying a job id reaches the model marked as a wake, naming the job and saying the operator is not present.
  • A wake that ran more than a minute after it was due says how late it is and when it was due; a punctual one says nothing about the clock.
  • A user entry with no job id reaches the model exactly as it was typed.
  • No event entry appears in a model request, except a failure, which appears as one derived line.
  • A wake whose run failed is followed in the request by a line saying it produced no reply, so an unanswered instruction is never mistaken for a repeated one.
  • Five consecutive ticks with identical status project to one line stating five occurrences and the time span.
  • Only the trailing run of ticks is collapsed; a run followed by a later user message is never re-collapsed.
  • Neither collapsing nor compaction removes an entry from the stored transcript.

Compaction

When a conversation passes a size threshold it compacts in place. The oldest turns are replaced, in what is sent, by a written summary of them. The recent turns are left exactly as they are. The session keeps its identifier, its jobs, its files, and its history.

BEFORE — 40,000 tokens              AFTER — 14,000 tokens
┌─────────────────────────┐         ┌─────────────────────────┐
│ system prompt    4,000  │         │ system prompt    4,000  │
├─────────────────────────┤         ├─────────────────────────┤
│ turn 1                  │         │ SUMMARY of turns 1-36   │
│ turn 2                  │         │ "Designed the session   │
│ turn 3                  │         │  model. Config fixed;   │   ~600
│   ...            36,000 │   ──▶   │  fork copies all; use   │
│ turn 35                 │         │  assistant role..."     │
│ turn 36                 │         ├─────────────────────────┤
│ turn 37                 │         │ turn 37                 │
│ turn 38                 │         │ turn 38          ~9,500 │
│ turn 39                 │         │ turn 39                 │
│ turn 40                 │         │ turn 40                 │
└─────────────────────────┘         └─────────────────────────┘

The threshold is chosen for cost, not for the model's context limit. Those limits now reach a million tokens, far past the point where every call becomes expensive: input is charged per token, so a session that has grown to eighty thousand tokens costs four times one at twenty thousand, on every single call and whether or not it is cached.

The recent turns survive verbatim because they are exactly what compresses worst and matters most — three options the agent just offered, a question waiting to be answered, the file it was working on.

Two thresholds

SettingDefaultControls
compact_at_tokens40,000What a call costs at its most expensive.
keep_verbatim_tokens10,000How much of the conversation is never lossy.

They are independent, and together they are the whole trade between cost and retention. Each compaction frees the difference between them, so the conversation grows by about thirty thousand tokens between one compaction and the next. Setting the tail close to the threshold would compact constantly for very little gain; the default keeps the tail at about a quarter.

Both are per-session, fixed when the session is created. A setting changed in configuration does not move underneath a conversation that is already running.

Where the split goes

Count backwards from the end, adding whole turns, until the next one would not fit in keep_verbatim_tokens. Everything before that point is compacted.

   turn 40   2,000  ┐
   turn 39   3,000  │  running total 9,500  →  KEEP
   turn 38   1,500  │
   turn 37   3,000  ┘
─────────────────────  split
   turn 36   2,500     would make 12,000 > 10,000  →  COMPACT
   turn 35     ...
   turn 1      ...

A turn is a user message and everything that followed it up to the next one. It is compacted whole or not at all: never half an exchange, and never an assistant message separated from the tool results it produced. The budget is a size rather than a message count, because messages range from a line to a whole file.

Growth is measured on the messages as the model would receive them, not on their text. A session that spends its context on tool results — fetched pages, command output — carries almost nothing in the text of its own turns, and measuring text alone would let it grow indefinitely without ever compacting.

How the summary is written

One model call, made between turns, on the session's own model. One model is used throughout the system. The call carries no tools, and it is not a turn in the conversation: the transcript records its result, never its asking.

The summariser is sent the previous compaction's text and the entries since it — never the raw entries the previous compaction already covered. So the cost of a compaction depends on how much was added since the last one, not on how long the conversation has become, and the two hundredth compaction costs what the second did.

It is asked to produce four headings, omitting any that would be empty:

## Decisions   what was settled, and the one-line why
## Open        questions unanswered, work in flight
## Facts       paths, names, numbers, shapes discovered
## Rejected    what was tried and did not work, so it is not retried

"Decisions" carries the reason and not only the conclusion, because a conclusion without its reason is re-litigated the next time it is inconvenient. "Rejected" exists because an agent that forgets what failed repeats it.

The summariser edits; it does not re-summarise. Existing lines are copied through unchanged unless something later supersedes them. This is the defence against generation loss: material compacted ten times has been through ten model calls, and a summary that is rewritten each time degrades like a photocopy of a photocopy. A summary that is edited each time only degrades in the lines that were actually touched.

Nothing is deleted

      ON DISK (append-only)              SENT TO MODEL (projection)
      ─────────────────────              ──────────────────────────
      prompt entry (superseded)
      turn 1        ┐
      turn 2        │  covered
      ...           │
      turn 36       ┘
  ▶   PROMPT entry (refreshed)  ·······▶  system message
  ▶   COMPACTION entry          ·······▶  the summary
      turn 37                   ·······▶  turn 37
      turn 38                   ·······▶  turn 38
      turn 39                   ·······▶  turn 39
      turn 40                   ·······▶  turn 40

A compaction only appends. The covered entries stay on disk, stay in the full-text index, and stay retrievable by session_search — including by the session that compacted them. Detail leaves the context; it does not leave the system. That is what makes compaction safe rather than lossy: the agent can go back and look, deliberately, when it needs to.

Memory is refreshed here

A compaction writes a new prompt entry before it writes the compaction, carrying memory as it stands now. This is the only moment a session's prompt changes.

It has to happen somewhere. A session has no end, so memory written during a conversation would otherwise never reach it, and the agent would write items it could never read. A compaction is the right place because it is the only moment where the prompt can change for free: the cached prefix is being discarded regardless.

A compaction can also be asked for, which is how a memory written a moment ago is made to take effect now rather than in thirty thousand tokens.

When it fails

CaseWhat happens
The model call failsNo compaction. An error event records it. The conversation continues, over threshold, and tries again after the next turn.
The summary is not smaller than what it coversRejected, nothing is appended. A summariser that restates rather than summarises must not be allowed to grow the conversation.
The summary leaves something outThe compaction entry is editable. An edit changes what the next turn sends.

A conversation that cannot compact keeps working. It gets more expensive, visibly — the size is on screen — and it does not stop, lose anything, or fail a turn.

Acceptance criteria

  • Passing the size threshold compacts the session in place; no new session is created and the identifier does not change.
  • A compaction appends a refreshed prompt entry and a compaction entry, and modifies no existing entry.
  • The entries a compaction covers remain on disk and remain findable by search, including from the session that compacted them.
  • The tail left verbatim fits keep_verbatim_tokens, and a turn is covered whole or not at all, including its tool results.
  • A second compaction reads the first compaction's text and the entries since, never the entries the first one covered.
  • The summary is written by the session's own model, in one call, with no tools.
  • A fact recorded in an early compaction is still present verbatim after ten further compactions.
  • A summary not smaller than what it covers is rejected and nothing is appended.
  • A failed compaction writes an error event, leaves the transcript otherwise untouched, and the next turn still runs.
  • The compaction text is editable, and an edit changes what the next turn sends.
  • The prompt entry a compaction writes carries memory as it stands at that moment.
  • Compaction can be requested, and takes effect immediately rather than at the threshold.
  • Compaction happens only between turns, never during one.
  • Both thresholds are configurable, are fixed per session at creation, and default to forty thousand and ten thousand projected tokens.
  • Growth counts the projected messages, so a session growing only in tool results still compacts.

Caching

A cache marker names a prefix, not a block: everything from the start of the request up to and including the marked position. The match must be exact from the first byte.

One marker is placed, at the end of the message list, and rewritten on every call. Each call reads the prefix the previous call wrote and writes one slightly longer. A conversation only ever grows at the bottom, so the prefix above is always a valid match.

  [system prompt]   4,000  ██
  [compaction]        600  ██
  [turn 37]         2,400  ██   cached: read at a tenth of price
  [turn 38]         3,100  ██
  [turn 39]         4,000  ██ ◀── marker, moves down every call
  [turn 40 · new]   1,000  ░░   full price

A cache write costs more than an ordinary call and a cache read costs far less, so a block read twice has already paid for itself. Everything above the marker is read at a tenth of its price; only what was added since the last call is paid for in full.

Only providers that require an explicit marker are given one. The rest cache the longest matching prefix themselves, and a marker would add nothing.

The idle gate

The one way to lose money is to write a cache that nobody reads, so a marker is placed only when another call is expected before it expires: a short lifetime when the operator was talking recently, a long one when a job that makes a model call is due, and no marker at all otherwise. An agent sitting idle overnight writes nothing and pays no premium for it.

A compaction resets it

A compaction rewrites the head of the message list, so the next call matches no prefix and writes a fresh one. One miss, then it rebuilds. This is bounded and rare by design — once per thirty thousand tokens of growth — and it is the same moment at which the prompt is allowed to change, for the same reason: nothing is lost that was not already being discarded.

It is visible

Caching changes what a conversation costs, so it is shown rather than inferred. Three things, each of which moves when something real moves:

  • The session header carries the size of the live cache and the time until it expires, counting down.
  • Each assistant message carries what the call that produced it actually hit, measured and not estimated.
  • A compaction says that it reset the cache, so the one moment the cache dies is legible where it happened.

A lifetime is not shown per message. A cache is one prefix with one expiry, so a per-message countdown would print the same number beside every message and tell the reader nothing.

Acceptance criteria

  • A request carries at most one cache marker, at the end of the message list.
  • No marker is written when no further call is expected before it would expire.
  • No marker is written for a provider that caches without one.
  • The first call after a compaction reports no cache hit; the call after that reports one.
  • The interface shows the live cache size and a countdown to its expiry, and shows it as expired when it is.
  • Each assistant message reports the cached proportion of the call that produced it, from what the provider reported.
  • A compaction states in the transcript that it reset the cache.

Forking

A fork copies a conversation into a new session. Everything comes across: the whole transcript, compactions and all, and a copy of the working directory. The original is untouched, stays active, and keeps its jobs.

It is the only way to change a configuration, and it is also how a conversation is branched — two directions explored from the same point, both readable, neither disturbing the other.

The fork gets a new identifier, and records the origin in forked_from. No identifier ever comes to address different content. The origin is not archived, not redirected, and not modified beyond one fork event saying where the copy went.

Compact, then fork. A fork carries everything, which is right when the point is to keep what was said. When the point is a clean slate under a new configuration, compact first and then fork: the copy carries the summary and the recent tail instead of the full history. Two operations compose into the third, so there is no third operation.

Jobs do not move. A job belongs to the conversation it was created in, which still exists and is still running. A fork that should carry the schedule creates it again, deliberately, in the fork.

Acceptance criteria

  • A fork copies every transcript entry of its origin, in order, including compaction and prompt entries.
  • A fork starts from a copy of its origin's working directory; writes after that are independent.
  • The origin stays active, keeps its jobs, and is modified only by one fork event.
  • The fork records its origin, and the interface links both ways.
  • A fork accepts a configuration; anything not given is inherited from the origin.
  • Jobs are not copied and not moved.
  • Forking is available from the interface.

Ordering

A session executes strictly one turn at a time. User messages and job runs enter the same queue for that session, and a job never interleaves with a turn in progress.

Acceptance criteria

  • Two turns never run concurrently in one session.
  • A job firing while a user turn is running waits and then runs.
  • A user message queued behind a job run is not reordered ahead of it or dropped.
  • Different sessions run concurrently without blocking each other.

Working directory

Each session owns a directory. Its tools run in it, its uploads land in it, and a relative path in a tool call means a file in it. Nothing is shared: two conversations writing notes.txt write two files.

A fork carries files as well as words: it starts from a copy of the origin's directory, so the copy continues with the files the conversation was working on, and neither session's later writes reach the other. A compaction touches the directory not at all — the session is the same session, and its files are where it left them.

Acceptance criteria

  • A session's tools run in that session's directory, and no other session's tools can read it.
  • A file uploaded to a session is written there, and its tools see it immediately.
  • A fork starts from a copy of its origin's directory; writes after that are independent.
  • A compaction leaves the working directory unchanged.
  • The files a session holds are listed, downloaded, and deleted through the API.
  • A path that would leave the session's directory is refused.
  • Deleting a session deletes its directory.
  • A session reports what it occupies on disk: its transcript and its working directory.

Export and import

A session travels as one zip: meta.json, transcript.jsonl, jobs.json, job_runs.json, and the working directory under files/. The archive mirrors what is on disk, so it can be read without this program.

An import restores the session under the identifier it already carries: a restored conversation is the one it was rather than a copy of it, and its links, its jobs, and its files all still name it. An identifier already present is therefore a conflict and the import is refused rather than merged.

Memory is not in it. Memory is durable across every conversation rather than owned by one, so an archive that carried it would change what every later session is told, silently, on import. An export is a session and nothing wider.

Acceptance criteria

  • An export carries the session's metadata, transcript, jobs, their run logs, and working directory.
  • An import restores all of them, in whichever agent reads the archive.
  • An imported transcript is searchable and its jobs run.
  • An import naming a session already present is refused, and says which.
  • An archive that is not a session is refused and nothing is altered.
  • Memory is not exported.

Search

A session_search tool queries a full-text index over every transcript entry ever written. It has two jobs, and the second is the one compaction depends on.

Reaching back into this conversation. A compaction takes detail out of the context but not out of the index. What the agent can no longer see it can still look up, so a conversation that has compacted ten times has its whole history a deliberate call away. This is what makes compaction a compression rather than a loss.

Reaching into another conversation. Sessions are otherwise sealed from one another: nothing from one appears in another by default, and the only thing that crosses on its own is memory, which is visible in the prompt where it lands.

The default scope is this session. Searching one's own history is ordinary and expected; reading another conversation is a thing the operator should be able to see being decided. So the scope is a parameter, it defaults to the current session, and widening it is an act that appears in the transcript as one.

Acceptance criteria

  • Search defaults to the current session and returns matches from it alone.
  • Search widened past the current session returns matches from others, and the widening is visible in the transcript.
  • An entry a compaction covers is still returned by a search of its own session.
  • Each result identifies its session and position so the user can open it.
  • Event entries are searchable.
  • The index is rebuildable from transcripts alone.
