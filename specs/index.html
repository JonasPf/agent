Agent

A single-user autonomous agent that runs on your own hardware, reachable from your phone.

It holds long-lived conversations, schedules work that runs inside those conversations, and remembers what you tell it. It cannot modify the copy of itself that is running: tools and skills are files on a disk it may not write (ADR-033). What it can do is propose a change to the next copy — a branch, a pull request, a pipeline, and a person who merges it (ADR-036).

Design principle

Nothing happens that you cannot see. Every scheduled action is a row you can read. Every memory the agent carries is visible at the top of the conversation. Every check it performs leaves a line in the transcript. There is no background process whose effects appear without explanation.

This principle decides the arguments. Where a hidden mechanism would be cheaper or more capable, the visible one wins unless the cost is prohibitive.

What it is not

  • Not multi-user. One person, no accounts; a tailnet, or one password in front of it (ADR-038).
  • Not a hosted service. One container on hardware you control.
  • Not a coding agent. It can write code, but its purpose is standing tasks and recall.

Cross-cutting requirements

R1 — Documentation is concise

All documentation — this specification, tool manifests, skills, README, code comments — states what is true in the fewest words that remain unambiguous. Documentation that restates the code, narrates history, or hedges is a defect.

Acceptance criteria

  • Every page in this specification is readable end to end in under five minutes.
  • Every feature states acceptance criteria; no feature is described only in prose.
  • No document describes implementation steps, migration history, or the state of the work.
  • A tool manifest's description is one sentence. A skill's description is one line.
  • Any document that duplicates another is deleted rather than cross-referenced.

R2 — Everything the agent does is inspectable

Any action taken on the user's behalf is recoverable from stored state without reading logs.

Acceptance criteria

  • Every model call belongs to a session whose full transcript is retrievable.
  • Every scheduled action exists as a job row before it runs and leaves an entry after it runs.
  • Every message the agent did not produce in direct reply to the user is attributed to its cause.
  • No state affecting agent behaviour exists only in a system prompt the user cannot read.

R3 — Single operator

The system serves exactly one person and holds no concept of accounts, roles, or sharing.

Acceptance criteria

  • No login, session cookie, or authorisation check exists in the application.
  • Network reachability is the only access control.
  • No stored record carries an owner or tenant identifier.

R4 — The core is small

The core is the agent loop, the scheduler, the store, the gateway, and the tool registry. Everything the model can invoke is a tool on disk. A capability is compiled in only when it cannot work from outside the process, and the specification names it and says why.

This is the same argument as nothing happens that you cannot see, applied to the system itself. A capability on disk can be read, edited, and replaced by the person running it, and read by the agent. A capability compiled in can only be read by someone with the source and a toolchain.

Acceptance criteria

  • Every capability the model can invoke is a tool directory on disk, unless this specification names it as core and states why.
  • Adding, changing, or removing a capability requires no rebuild and no restart of the agent. A tool is built on its own and dropped in; the process keeps running and picks it up on a reload (ADR-035).
  • A tool reaches the system through the same HTTP API the interface uses, never through a private hook.
  • No tool holds a power the core withholds from other tools.

R5 — Every criterion is demonstrated end to end

Each acceptance criterion in this specification is covered by a test that drives the system through a surface something outside it actually uses: the HTTP API, the WebSocket, the web interface in a browser, or a tool run as the subprocess it really is. The store is the real store on disk, a tool is the real executable, and a job is fired by the real scheduler.

Only what lives outside the container may be substituted: the model provider and the public web. Everything inside is exercised as shipped. A test that reaches past the surface to call an internal function is a unit test — worth having, and not a substitute. A criterion is discharged by showing the behaviour, not by showing that a function that contributes to it returns the right value.

Why the surface and not the seam. Every defect this specification has cost so far lived between components that were each correct: a tool result the interface could not parse, a firing signal the scheduler read and the transcript did not record. A test that mocks the neighbour cannot see that class of fault, which is the class this system produces.

What this cannot reach is the model's own judgement. An end-to-end test substitutes the model provider, so it can show that the system handles a tool call correctly and can say nothing about whether a model reads the tool's description correctly. That is what evals are for, and they are evidence rather than a gate: every tool carries them, and the test run enforces that it does.

A criterion that genuinely cannot be observed from outside — purity, or an internal invariant — says so where it is written, and names what covers it instead. That exception is written down rather than assumed, so an untested criterion is always visible as one.

Acceptance criteria

  • Every acceptance criterion carries an identifier, and every end-to-end test names the identifiers it covers.
  • A criterion with no test naming it is reported by the test run, not discovered by reading.
  • No end-to-end test replaces a component of the system with a substitute, other than the model provider and the public web.
  • Interface criteria are exercised in a real browser against the real gateway.
  • A criterion exempted from end-to-end coverage states the reason where it is written.
