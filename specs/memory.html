Memory

What the agent carries between conversations, visible at the top of every one.

Context is what is on screen now. Memory is what survives it. They are different things and are stored differently.

One store

There is a single memory, shared by every session. Nothing scopes a read: a session does not have a memory of its own, and there is no way to ask for only the items one conversation wrote. The source_session field records where an item came from so it can be traced back, and is never used to filter what is loaded.

This is the one thing in the system that crosses a session boundary on its own. Transcripts are separate, working directories are separate, and search defaults to the current session. Memory is the deliberate exception, and it is paid for by being visible: every item in force is listed in the prompt entry, in the conversation it is acting on.

Visible recall

Memory is loaded automatically into the system prompt. It is not hidden there: the system prompt is itself an entry of the transcript, and memory is one of its sections — the only editable one.

┌─ prompt · 4,180 tokens                          ─┐
│  persona             310 tokens         expand   │
│  memory · 12 items   480 tokens    edit collapse │
│    • prefers Go                                  │
│    • sqlite, never a vector database             │
│    • answers: lead with the action               │
│    …9 more                                       │
│  skills · 6          190 tokens         expand   │
│  tools · 12        3,200 tokens         expand   │
└──────────────────────────────────────────────────┘

you:   what did we decide about the database?
agent: sqlite, one table prefix per tool.

Loading is automatic so recall does not depend on the agent thinking to look. Rendering is visible so its influence on an answer can always be traced.

Acceptance criteria

  • Every prompt entry contains a memory section listing every item in force when it was written.
  • Deleting an item from the section deletes it from storage.
  • A session with no memory shows an empty memory section rather than omitting it.
  • Memory forms part of the cacheable prefix and does not change between compactions.

Writing

The agent writes memory through a tool call, which appears in the transcript where it happened. The item is stored immediately and is in force from that moment for every session created afterwards.

It reaches a conversation that is already running at that conversation's next compaction, which writes a fresh prompt entry carrying memory as it then stands. That is true of the session that wrote the item and equally true of every other session running at the time: the store is one store, and a compaction reads it as it is. Until then a conversation runs on the prompt it already has — the session that wrote the item knows it because it just wrote it, and the transcript says so.

So a memory does reach other live conversations. Not immediately, and not invisibly: it lands at a compaction, which writes a prompt entry naming every item in force and says in the transcript that memory was refreshed. This is the intended reach — an agent that learned something in one conversation should not go on being wrong about it in another — and it is the reason memory is capped, consolidated by hand, and rendered item by item rather than summarised.

Acceptance criteria

  • A memory write is a visible transcript entry naming what was stored.
  • Memory is a single store; no read is scoped to a session, and source_session never filters what is loaded.
  • A written item is in force for every session created after it.
  • A write appends to the end of the transcript and modifies no existing entry.
  • A written item appears in the memory section of the next prompt entry any session receives, not only the session that wrote it.
  • A compaction writes a prompt entry carrying memory as it stands at that moment.
  • A compaction can be requested, which is how a memory is made to take effect without waiting for the threshold.
Why it waits for a compaction. Rewriting the memory section at an arbitrary moment would change the system prompt and throw away the cached prefix for the whole conversation. A compaction is throwing that prefix away regardless, so it is the one moment where the prompt can change for nothing. It is also announced: the transcript shows the new prompt entry where it was written, and the compaction that occasioned it says memory was refreshed. Memory never moves underneath a conversation unseen.
Why memory refreshes and tools do not. Memory is text the model reads; a tool is a definition it programmes against. Changing the callable set mid-conversation is what ADR-019 removed, and a compaction does not bring it back — a new tool still needs a new session, reached by forking. Only the memory section of the prompt is rewritten.

Consolidation

Memory has a fixed capacity. A write that would exceed it fails and returns an error stating what is already stored. The agent must then remove or merge items before retrying, in the same turn.

Failing loudly is deliberate. Silently dropping the oldest item produces an agent that quietly forgets and cannot tell you it has.

Acceptance criteria

  • A write exceeding capacity returns an error and stores nothing.
  • The error names the current items so consolidation can be done without a further lookup.
  • No item is ever removed automatically.
  • Capacity defaults to 8,000 characters, is configurable, and is shown in the interface alongside current usage.

Relationship to search

Memory is curated and small. Transcript search is exhaustive and large. Memory answers "what is always true"; search answers "what was said that one time". Neither replaces the other, and search is described under Sessions.
