AGENT SPEC Overview Architecture Sessions Jobs Tools Skills Memory Web UI API ADRs

Decisions

Thirty-five choices with real tradeoffs. Each states what was given up.

ADR-001 · accepted

Write the agent loop rather than adopt a framework

Context

The loop that assembles a request, calls a model, dispatches tool calls, and repeats is a few hundred lines. Existing agent frameworks provide it along with abstractions for tools, memory, and sessions, all of which this system defines differently.

Decision

Implement the loop directly against an OpenAI-compatible client. Adopt no agent framework.

Consequences

Full control over projection, caching, and per-session tool sets, which every framework models differently or not at all. In exchange, streaming tool-call reassembly, interrupt handling, and provider quirks must be handled here. This is the smallest component in the system, and it is the one every other decision depends on.

ADR-002 · accepted

Reach models through OpenRouter only

Context

Talking to a provider directly gives the cleanest access to that provider's features. A broker gives one credential, one wire format, and hundreds of models.

Decision

Use OpenRouter exclusively, over its OpenAI-compatible API.

Consequences

Model choice, per-model pricing, context windows, and remaining credit are all available as endpoints, which turns four interface requirements into API calls rather than hand-maintained tables. The cost is that caching behaviour now varies by provider: some cache automatically, others require explicit markers, and prompt assembly must branch on which. Streaming tool-call deltas are also less consistent across providers than they are against a single vendor.

ADR-003 · accepted

SQLite and flat files; no vector database

Context

Recall across conversations is usually built on embeddings and a vector store.

Decision

Store transcripts as append-only files and everything else in SQLite with a full-text index. Add no embedding model and no vector store.

Consequences

The whole system is one file plus a directory, backed up by copying and rebuilt by replaying. Search matches words rather than meaning, so a query phrased differently from the original text can miss. Curated memory carries the weight that semantic search would otherwise carry, which is why memory is small and deliberate rather than automatic.

ADR-004 · accepted

One container, one user, no privilege separation

Context

The agent writes executables and runs them. Those executables run beside the gateway, the scheduler, the database, and the model API key. Separating them into another user or another container is possible and would bound the damage.

Decision

Run the gateway, the agent, and all tools as one user in one container. (This decision originally added a git repository over the workspace, committed on every tool reload; ADR-017 removed it.)

Consequences

A tool the agent writes can modify the scheduler, read the key, and alter the database. The realistic failure is not attack but accident, and an accident is repaired by editing the tool that caused it. This is acceptable for a single-operator system on private hardware and would not be acceptable if the system were shared or exposed. Revisit if either changes.

ADR-005 · accepted

Tailscale only; no authentication in the application

Context

The interface must work from a phone. That normally means public exposure and therefore login, sessions, and abuse handling — for a service whose main feature is running arbitrary code.

Decision

Publish nothing to the public internet. Serve over Tailscale, which supplies a stable hostname and a trusted certificate. Treat network reachability as the only access control.

Consequences

Authentication, session cookies, cross-site request forgery, and rate limiting leave the specification entirely. The cost is that the interface is unreachable when the tailnet is down, and sharing anything with another person is impossible without changing this decision. Since ADR-026 there is no outbound notification path either, so a phone off the tailnet learns nothing at all until it reconnects.

ADR-006 · accepted

Jobs run inside the conversation that created them

Context

Scheduled work is usually given a fresh session with no history, which is cheap and keeps the conversation clean. The alternative is to run it in the conversation where it was requested.

Decision

A job holds a session identifier and runs there. There is no separate session kind for scheduled work.

Consequences

The job's instruction does not have to restate its own context — which deploy, which repository, what the user cared about — because the conversation already contains it. Removing that translation step removes the most common source of a job doing the wrong thing. Results appear where the request was made. The costs are that model-invoking ticks replay the conversation, making caching essential rather than optional, and that those ticks accumulate in the transcript and bring rotation forward. Both are mitigated by ADR-008 and ADR-009, which together keep most ticks free and most tick output out of context.

ADR-007 · accepted

No heartbeat

Context

Comparable systems wake the agent every thirty minutes in its main conversation to look for anything needing attention. It catches open loops nobody scheduled.

Decision

Do not implement a heartbeat. Proactive behaviour comes only from jobs the agent creates explicitly when asked.

Consequences

Every future action is a row that can be read, edited, and deleted before it happens. When the agent misunderstands a request, the mistake is visible immediately rather than at three in the morning. Forty-eight full-context turns a day disappear, which is the single largest recurring cost in the designs that have one. What is lost is the catch-all: a commitment the user never phrased as a request is never noticed. That mechanism was unreliable — it depended on the model re-reading a long conversation and spotting something — and a job's run log covers the failure that matters, which is a job that has been waking for weeks without its condition ever being met (ADR-028).

ADR-008 · accepted

Evaluate deterministic conditions without the model

Context

Most of what people ask to be told about is a fact, not a judgement: an exit code, an HTTP status, a file appearing. Systems that spawn an agent for every scheduled run pay a model call to read a status code.

Decision

A job may carry a check: a shell command whose exit status decides the question. The model runs only when it exits zero. A job without a check calls the model every tick and may not tick more often than every fifteen minutes. (ADR-029 later removed that floor; the rest stands.)

Consequences

A two-minute poll costs nothing until the moment it fires, which makes frequent polling reasonable and makes ADR-006 affordable. A check-less job, by contrast, runs on its session's model in its session's context, so its cost is whatever a turn in that conversation costs. Nothing about a job is configured separately — no model of its own, no context of its own — because the rotation threshold already bounds what a turn can cost, and a second set of knobs would only hide the price.

The agent must therefore decide whether a condition is expressible as a command, and sometimes it will reach for judgement where a command would have done. Three things push against that: the scheduling skill treats a check as the default, a check-less job has to record why no command would work, and the fifteen-minute floor bounds the cost when it still happens. Two of those three are since gone — reason_no_check with ADR-023 and the floor with ADR-029 — leaving the skill, and the cost visible on the job rather than capped.

ADR-009 · accepted

What is stored is not what is sent

Context

Visibility and cost pull in opposite directions. Seven hundred daily check results make a conversation legible and unaffordable at the same time.

Decision

Keep the complete transcript. Derive the model's message list from it through a single projection that drops event entries, collapses consecutive identical job ticks into one line with a count, and passes everything else through.

Consequences

The conflict dissolves: every tick is visible and nearly all of them are free. All future context handling belongs in one pure function that can be tested directly. The risk is drift — what the user reads and what the model read are no longer identical — so the interface must make clear which entries were never sent.

ADR-010 · accepted

The system prompt is the first entry of the transcript

Context

A system prompt is normally invisible: the agent's persona, its memory, and the definitions of every tool it can call all shape its behaviour from outside the conversation. Memory is the sharpest case — retrieved by a tool it is visible but unreliable, since the agent must decide to look and cannot know what it does not know; placed in the prompt it is reliable but hidden.

Decision

Assemble the system prompt as usual, then write it as the session's first entry, split into expandable sections with token counts. Memory is one of those sections, and the only editable one. Because entries are immutable, later changes — a tool toggled, a memory written, the model changed — each append their own entry where they occur.

Consequences

Nothing that shapes behaviour lives outside the conversation, so requirement R2 is satisfied by construction rather than by an extra endpoint. Recall stops depending on the agent's judgement, and any answer can be traced by scrolling up. A wrong memory is corrected in place instead of by asking the agent to correct itself. Token counts per section make context bloat visible at the point where it is caused. The entry itself is never sent, so it costs nothing. The cost is that the prompt's current state must be read as the opening entry plus the changes after it, rather than as one canonical document; sections are collapsed by default because tool definitions are long.

ADR-011 · superseded by ADR-026

Two notification tiers, with the agent choosing between them

Context

Notifying on everything trains the user to ignore notifications, which fails silently and completely. Notifying on nothing defeats the purpose of a phone interface.

Decision

New assistant output updates a silent badge. Interrupting notifications are sent only when the agent calls a notify tool, or when a dead letter or the circuit breaker fires. The latter two cannot be suppressed.

Consequences

The agent writes the notification, so it says what happened rather than showing a truncated first line, and the decision to interrupt is a visible tool call that can be audited and corrected. The risk is under-notification: the agent stays quiet when the user wanted to know. The two unsuppressable triggers cover the cases where silence would be worst.

Superseded. The tiers were built and did not deliver. See ADR-026.

ADR-012 · accepted

No subagents

Context

Isolating a long sub-task keeps a conversation lean. This matters more here than elsewhere, because ADR-006 means anything bloating a conversation is replayed by every job attached to it.

Decision

Do not implement subagents. When work should be isolated, the user opens another conversation.

Consequences

One session kind, no spawning, no fan-out, no result-summarisation protocol, and no nesting rules. The cost is that the agent cannot isolate work on its own initiative, so a long tool-building session in a conversation that also holds a job will be replayed by that job. The mitigation is convention rather than mechanism: build tools in their own conversation. Revisit if that convention proves too easy to forget.

ADR-013 · superseded by ADR-021

The notify tool is the firing signal for judgement jobs

Context

A job with a check has an unambiguous trigger: the command exits zero. A job whose condition needs judgement produces prose, and something has to decide whether that prose means the condition was met. The alternatives were parsing a sentinel out of the reply, or requiring a structured verdict alongside it.

Decision

A judgement job fires when the model calls the notify tool during its run. A run that does not call it is recorded as an event with status not_fired and produces no message.

Consequences

Firing, notifying, and recording become one auditable act rather than three mechanisms that can disagree. Nothing parses prose, so a job cannot fire because of a stray word. The sentinel field this replaces is deleted. Every tick gains a status, which is what allows the projection to collapse quiet runs — without it, judgement polls would never collapse, and those are the only ticks that cost money. The cost is that a job cannot fire quietly: firing always interrupts. A condition worth polling for that is not worth a notification has no expression here, and would need a second, silent signal if one is ever wanted.

ADR-014 · superseded by ADR-016

Availability is enforced at dispatch, not by editing the prompt

Context

Tools and skills should be switchable per session, including mid-session. The obvious implementation is to include only the enabled ones in the prompt. That makes every toggle rewrite the prefix and therefore pay a full cache write across the whole conversation — worst on exactly the long, job-bearing sessions where toggling is most useful.

Decision

Always include every tool definition and skill description in the prompt. Keep the enabled set as session state, append an entry naming it whenever it changes, and refuse calls to anything not enabled.

Consequences

Toggling becomes free and instant, and the prompt is fixed for the life of a session, which is what makes its cached prefix durable. It generalises: a tool written mid-session is appended the same way and needs no prompt rewrite either. The costs are that the prompt always carries every definition, so a session using three tools still pays for thirty — at cached rates, and only once — and that the model can attempt a disabled tool and waste a call. The appended entry tells it what is available; the refusal catches it when it forgets.

Why it was superseded

The costs turned out to be structural rather than incidental. Keeping the prompt honest required an entry to announce each change, a dispatch check to refuse calls, and a permanent gap between what the prompt defines and what the session can do — and the gap had to be explained everywhere it surfaced. ADR-016 takes the requirement away instead of paying for it.

ADR-015 · accepted

Summarise continuously and rotate, rather than compact

Context

The usual answer to a full context window is compaction: at the limit, summarise the older messages and continue in the same session. That does expensive work at the worst moment, rewrites the cached prefix exactly when the conversation is longest, and leaves a session that is half transcript and half summary.

Decision

Maintain a rolling summary of every session, updated incrementally as the session grows, stored beside the session rather than in its prompt. At the context limit, open a successor session seeded with that summary and archive the predecessor. Forking a session and resuming an old one are the same operation, asked for rather than automatic.

Consequences

Reaching the threshold costs nothing, because the summary already exists. The successor starts with a short, clean prefix that caches from its first turn, instead of a rewritten long one. Each update is bounded by how much was added rather than by the conversation's length, so it stays cheap on the session's own model and the system never has to choose a second one. Three features — rotation, fork, resume — become one mechanism and one field. Compaction is deleted along with its event kind, its markers, and the interface for expanding them.

The summary must stay out of its own session's prompt: putting it there would rewrite the prefix on every update, which is the cost this decision exists to avoid. Exact history is not lost, since the predecessor's transcript remains searchable, but the model can no longer quote it directly — it has to search. Rotation is also a visible discontinuity, so it happens only between turns, never mid-task.

A summary alone would still make that discontinuity sharp, because the most recent exchanges are what a summary compresses worst. The successor therefore carries the last complete turns that fit a token budget as well. Budgeting by size rather than by message count keeps the successor's starting size predictable, which is what rotation exists to control.

Rotation is triggered by size, not by cache expiry and not by the context limit. Absorbing a cold cache is cheap; discarding a live conversation to avoid it would trade continuity for almost nothing. Context limits are the wrong trigger for the opposite reason — at a million tokens they are far beyond the point where every call has become expensive. The threshold is a cost decision and is configurable.

ADR-016 · accepted, amended by ADR-019

A session's configuration is fixed; rotation is how it changes

Context

ADR-014 made tools and skills switchable mid-session by always defining every one of them in the prompt and refusing calls to the rest. It worked, and it left the prompt permanently out of step with the session: definitions present for tools that cannot be called, an appended entry to say which, a dispatch check to enforce it, a distinct error for a skill that exists but is off, and a job created on Monday able to run on Wednesday under different rules. The model was, separately, the one setting that did rewrite session state mid-conversation, with its own entry kind.

Decision

Treat model, tools, and skills as one immutable configuration chosen at session creation. The prompt defines exactly the enabled tools and indexes exactly the enabled skills. Changing any of it is a rotation: the conversation continues in a new session under the new configuration, carrying its summary, recent turns, and jobs across. Rotation, fork, resume, and reconfiguration become one operation.

Consequences

Five special cases disappear: the availability entry, the model-change entry, the dispatch refusal, the disabled-skill error, and the divergence between the prompt and the session. The prompt a session is sent on its last turn is the prompt it was sent on its first, so position zero is a description rather than a snapshot. Caching is unaffected, because a changed configuration was always going to be a changed prefix and now it is honestly a different session. The cost is that changing one setting starts a new conversation, which is heavier than a toggle — the carry-over makes it cheap, but it is not free, and it is deliberately the same weight as any other rotation. A session that wants twelve tools still defines twelve; one that wants three now defines three, and pays for three.

ADR-017 · accepted

The workspace is not version controlled

Context

ADR-004 answered "the agent can break itself" with a git repository: commit on every tool reload, so a bad tool is reverted rather than reconstructed. The mechanism never worked as described. The repository had to be rooted at a directory holding the workspace, the tools, and the skills, which is not the workspace but its parent — and outside a container that parent is the operator's own source checkout, so the agent committed the operator's work as its own. Startup staged everything it found and committed with --allow-empty, producing one commit per boot, all with the same message. Nothing ever read the history back: there is no revert path in the product, no interface onto it, and no acceptance criterion that exercises one.

Decision

Remove it. The agent creates no repository, makes no commits, and has no opinion about version control.

Consequences

A tool that breaks the system is fixed by editing the tool, which is what actually happened anyway. The safety argument in ADR-004 loses a clause it was not honouring; what is genuinely lost is a recovery path that was never built, not one that was working. An operator who wants the directory versioned can keep it in a repository of their own, on their own terms — the agent no longer competes with them for it. The system now has no automatic recovery from a self-inflicted break, which is the honest position for a prototype and is worth revisiting with a mechanism someone would actually use.

ADR-018 · accepted

Settings come from the environment, backed by a file the environment overrides

Context

Every setting, including the model API key, was read from the process environment alone. That is correct for a container, where the environment is declared once and reproduced on every start, and poor everywhere else: outside one, the settings live in whichever shell last exported them. The key is the sharp case. Its absence does not fail at startup — the agent warns and runs — it fails hours later, inside a scheduled job, as three retries and a dead letter.

Decision

Read a file of KEY=VALUE lines from the working directory at startup and fill in anything the environment has not already set. The environment wins. The file is optional, covers every setting rather than the key alone, and is excluded from version control.

Consequences

The container path is unchanged: an environment declared there overrides a file that is not present anyway. Outside one, the settings survive a new terminal and a reboot.

The precedence runs this way because the opposite is a trap. A file that beat the environment would make an explicit override on the command line silently do nothing, and the failure would look like the override being wrong rather than being ignored — a worse bug than the problem the file solves.

The cost is a credential sitting in a plaintext file, which is a real weakening: anything that can read the working directory can read the key, where before it had to read a process's environment. For a single-operator system on private hardware that is the same threat model ADR-004 already accepted, and the file is mode 600 with a startup warning when it is not. It would not be acceptable on a shared machine, and a secret manager is the answer there rather than a better file.

ADR-019 · superseded by ADR-022

A configuration settles at the first turn, not at creation

Context

ADR-016 made model, tools, and skills one immutable configuration and wrote the prompt at the moment the session was created, which froze a session the instant it existed. In the interface that made forking a dead end. A fork inherits its predecessor's configuration and is fixed before the operator has seen it, so changing anything about a fork meant deciding it on a screen before the fork existed, while starting a fresh conversation meant opening a session and configuring it. The same act — continue from here under different settings — behaved two different ways depending on where it started.

Decision

The configuration settles at the session's first turn rather than at its creation. The prompt entry is written when the first turn is assembled. Until then the session has no prompt, and its model, tools, and skills are editable in place; from the first turn onward everything ADR-016 decided holds unchanged.

Consequences

Fork, open the controls, change the tools, send — the same sequence as starting a conversation, because they are the same operation. None of what ADR-016 removed comes back: there is still exactly one prompt per session, still no change mid-conversation, and still no gap between the prompt and the session, because a session that has not taken a turn has told the model nothing and has nothing to be out of step with. Position zero is still the prompt as sent — it is written when it is first sent rather than when it is first known.

Two costs. A session that has never run has no prompt entry, so the prompt is retrievable only once the session has taken a turn; before that the controls screen shows the configuration it would be built from. And the refusal on PATCH becomes conditional rather than absolute, which is one more state than a flat no.

ADR-020 · accepted

Keep the core small; ship capability as tools on disk

Context

Twelve tools were compiled into the binary. Each was a Go function with direct access to the store, the hub, and the scheduler. A tool on disk has none of that: it is a subprocess that must ask over the HTTP API. The compiled ones were faster to write and faster to run, and every one of them could have been a directory instead.

Decision

The core is the loop, the scheduler, the store, the gateway, and the tool registry. Everything the model can invoke is a tool directory on disk. A capability is compiled in only when running it outside the process would not work; today that is reload_tools alone, and the specification names it. Tools reach the system through the API the interface already uses, given AGENT_URL, AGENT_SESSION, and AGENT_JOB.

Consequences

Every capability becomes readable and replaceable without a toolchain, by the operator and by the agent — which is what the tools system was for, and which compiled-in tools quietly opted out of. The API stops being an interface convenience and becomes the system's one internal contract, so a capability the API cannot express is now visible as a gap rather than hidden behind a function call. The cost is a subprocess and a local round trip per call, and two new failure modes — exec and socket — that previously could not occur. Both surface as ordinary error results, so a turn degrades the same way it already did. A tool that needs something the API does not expose cannot be written until the API exposes it, which is a constraint on the core, deliberately.

ADR-021 · accepted

A judgement job records every run; notify is no longer a firing signal

Context

ADR-013 made calling notify the firing signal for a judgement job. A run that did not call it was buffered, discarded, and replaced by one event line. That kept transcripts short: a job polling every fifteen minutes wakes ninety-six times a day, and only the run that mattered was kept.

Decision

Delete the buffer and the firing signal. Every run of a judgement job is written to the transcript in full, attributed to its job. A judgement job reschedules after every run and ends by being deleted or by expiring. The model ends its own job by calling the schedule tool, an ordinary visible tool call. notify becomes what its name says: it sends a notification, and nothing else.

Consequences

The rule that nothing happens the operator cannot see now holds without exception; ADR-013 was the one place the system discarded its own work and reported a summary instead. notify loses its reach into the turn that called it, which is what let it move out of the core under ADR-020 — the two decisions are the same decision seen twice. The cost is real and was accepted knowingly: a polling job now spends context and money on runs that find nothing, and sessions carrying such a job rotate far more often. Firing and notifying are also no longer the same act, so a job can now decide its condition is met without interrupting, which ADR-013 could not express.

ADR-022 · accepted

A configuration is fixed at creation; the prompt is written there too

Context

ADR-019 let a session's model, tools, and skills stay editable until its first turn, so that forking and starting a conversation felt the same. The cost was a second state for a session to be in. Every surface had to branch on it: the interface showed a different notice, a different button, and a different action; PATCH refused conditionally rather than absolutely; a session could exist with no prompt entry, so anything reading position zero had to cope with its absence.

Decision

A session's configuration is fixed when the session is created, and its prompt entry is written at the same moment. There is no window in which a session exists and its configuration is open. The configuration is chosen before the session exists, on the screen that creates it — which is what forking and starting a conversation now both do.

Consequences

One state instead of two. Every session has a prompt entry from the moment it exists, so position zero is never absent and nothing downstream branches on whether it is there. PATCH refuses a configuration change flatly, with one answer rather than two. What ADR-019 was protecting is kept by moving the choice earlier rather than by keeping it open later: fork now opens the same configuration screen as a new conversation, and creates the session when it is confirmed.

The cost is that a fork is no longer one tap — it is a screen and then a tap. In exchange, a configuration cannot be changed after a session exists, which is the property the rest of the design already assumed everywhere else.

ADR-023 · accepted · until removed by ADR-028, floor removed by ADR-029

A job has no kind; scheduling is four independent fields

Context

A job was classified into one of three kinds — check, due, judgement — derived from whether it had a check and whether its schedule named a single instant. Behaviour then branched on the kind, and each kind needed exemptions from rules written for another: a reminder was exempt from the fifteen-minute floor, from reason_no_check, and should have been exempt from expiry but was not, so any reminder set further ahead than a day was deleted before it arrived. A recurring action with no condition — a daily briefing — was classified as a judgement and made to explain why no command could decide a question nobody had asked.

Decision

Remove the concept. A job is schedule, prompt, and three optional fields: check gates whether a wake acts, after_acting says whether the job survives a wake that did, and until stops waking. Nothing derives a kind and nothing branches on one. on_condition_met and reason_no_check are deleted, and no job receives a deadline it did not ask for.

Consequences

Sixteen catalogued requests, from a birthday months out to a two-minute deploy poll, are expressed in the same four fields with no exemption anywhere; the interface shows those fields rather than a label it computed. The scheduler collapses to one path: check if there is one, act, reschedule if repeating. The cost rule survives on its own terms — a recurring wake with no check runs a turn every time, so it may not recur faster than every fifteen minutes — and applies uniformly instead of being attached to a category. (ADR-029 later removed that floor as well.)

The third field was first called repeat. An eval showed models reading that as a question about cadence and answering it from the request's own words: "tell me when the deploy finishes, check every two minutes" set it true and left a finished watch firing forever, while the same request without the cadence phrase set it correctly three times out of three. A name describing the schedule cannot be asked a question about the job's ending, so it is named for the moment it applies to.

Two things are given up. reason_no_check was a nudge toward cheap checks, and it is gone; the scheduling skill and the floor are what remain. And with no default deadline, a job watching for something that never happens now waits indefinitely rather than giving up after a day — it stays a visible row, and until is there for requests that deserve one, but nothing volunteers it.

Amended. ADR-028 removes until as well, leaving three fields. A job that waits forever is now answered by reading its run log, not by a deadline that deletes it.

ADR-024 · accepted

A session owns a working directory

Context

Every session's tools ran in one shared workspace. Two conversations working on files of the same name overwrote each other, an upload had to be filed under a path the interface assembled by hand, and a fork continued the words of a conversation but not the files it was working on. Nothing said which conversation a file belonged to, so nothing could carry it, copy it, or delete it with one.

Decision

Each session owns a directory under the workspace, named for the session. Tools and check commands run in it, uploads land in it, and a relative path in a tool call resolves inside it. It is created with the session, copied when the session is continued — rotation, fork, and resume alike — and deleted with the session.

Consequences

Files gain the same lifecycle as the conversation that produced them, which is what makes an export possible at all: a session and its directory are one thing to carry. A path that would leave the directory is refused by the file tools.

Corrected. This decision claimed the isolation was "real rather than conventional". It was not: read, write, and edit refused an escaping path, and bash — a shell, which does what it is told — did not, so one session's tools could read another's files and the operator's API key. ADR-030 makes the claim true by moving the boundary into the operating system.

The cost is copying. A continuation duplicates the predecessor's directory, and rotation is automatic, so a conversation holding a large working directory pays for it every time it rotates. The alternative — successor and predecessor sharing one directory — was rejected because a fork's writes would then reach the session it was forked from, which is exactly what a fork is for avoiding. Nothing is shared by default any more: a tool that wants a place common to every session has to name one.

ADR-025 · accepted

A session exports as a zip and imports under its own identifier

Context

A conversation was only retrievable from the machine holding it. Moving one to another agent, or keeping a copy before deleting it, meant copying a session directory, the rows belonging to it in SQLite, and its files, and knowing which was which.

Decision

An export is one zip mirroring what is on disk: meta.json, transcript.jsonl, jobs.json, dead_letters.json, and the working directory under files/. An import restores all of it under the identifier the archive carries; an identifier already present is refused. Memory is not in the archive.

Consequences

An archive is readable with unzip and a text editor, so a backup does not depend on this program to be worth anything. Keeping the identifier means a restored conversation is the one it was: its links, its jobs, and its dead letters still name it, and re-importing after a deletion is a restore rather than a duplicate. The price is that restoring over a session still present is refused rather than merged — the identifier would otherwise address two different conversations, which is the one thing the design does not do anywhere.

Memory is left out because it is durable across every conversation rather than owned by one: carrying it would change what every later session is told, silently, on import. A job whose next run has already passed fires on the next tick after an import, exactly as it would for an agent that had been switched off.

ADR-026 · accepted · amended by ADR-027

No notifications at all

Context

ADR-011 gave the system two notification tiers and a notify tool for the agent to reach the operator with. All of it was built: web push with VAPID keys, a service worker, a subscription table, per-session muting, and a fallback that showed the notification inside the app when the operating system would not. None of it delivered a single notification on the operator's own devices. Each layer failed for a different reason — permission never granted, a browser that disables the push service by default, an origin without a secure context — and every failure looked the same from the outside: a reminder that quietly did not arrive.

Decision

Remove the whole stack. No notify tool, no push, no VAPID keys, no service worker, no in-app popup, no per-session mute. A reminder is the agent writing in the conversation, and nothing more. Unread work is a count in the session list; a dead letter has its own screen; a tripped breaker is a banner across the top of every screen.

Consequences

The agent can no longer reach the operator, so a reminder is only as timely as the next time they open the app. That is a real loss and it is the point: the previous design claimed a capability it did not have, which is worse than a system that plainly does not interrupt. Everything the agent does still leaves a visible record, so R1 holds — what changes is that the operator goes to the record rather than the record coming to them.

The removal also takes the project's last non-stdlib runtime dependency with it, and deletes the one part of the system whose behaviour could not be tested end to end: a push notification's delivery depended on a browser, an operating system, and a vendor push service, none of which is in the container.

Re-adding it later means re-deciding it. The pieces are small; the reason they were removed is that they did not work, not that they were expensive.

Amended. ADR-027 restores one narrow piece — the browser's own notification for an unread message, while a tab is open. The agent's ability to interrupt is not restored, and neither is push.

ADR-027 · accepted · amends ADR-026

The interface notifies about unread messages; the agent still cannot

Context

ADR-026 removed every notification because the stack that carried them did not work. It was right about the stack and too broad about the need: the operator still wants to know that the agent has said something while they were looking elsewhere. The part that failed was delivery to a device that is not running the app — push, VAPID, a service worker, a vendor service, a permission prompt behind an install. The part that never failed is the browser's own notification API, which needs none of that.

Decision

While a tab is open, a new assistant message in a conversation the operator is not currently reading shows a system notification. No push, no service worker, no keys, no subscription, no per-session mute. The agent is not involved: there is no notify tool, it cannot choose to interrupt, and it cannot suppress one. This is the interface reporting unread output, which is the badge tier of ADR-011 raised from a count to a banner — not the interrupt tier returning.

Consequences

The capability is honest about its limits, which is what the previous design was not: it works while the browser runs and does nothing at all otherwise, and the settings screen says which of those a device is in. A reminder is still only as timely as an open browser, so a phone with the app closed learns nothing — the same position as ADR-026, and the reason that decision is amended rather than reversed.

Everything here is client-side. No endpoint, no schema, no dependency, and nothing stored: the gateway is unchanged, and removing the feature again would mean deleting one file and one call.

ADR-028 · accepted

A job keeps its own run log; dead letters and expiry are removed

Context

A job's history lived in the conversation it fired into, which is the wrong place twice over: a transcript interleaves the job's wakes with everything else in that conversation, and a job outlives the session that created it, so a rotation left its past in a session it no longer belongs to. The question the operator actually asks — "has this been running, and what did it say?" — had no place to be answered.

Two mechanisms existed because of that gap. A dead letter was a copy of a job taken at the moment the system deleted it, so the evidence would survive the deletion. An until deadline existed so a job watching for something that never happened would eventually stop. Both are ways of managing a system that throws work away on its own.

Decision

Every wake writes a line to the job's own log: when it was due, when it ran, whether it fired, skipped, or failed, and what was said. The log is stored against the job, travels with it in an export, and is deleted only when the job is.

Dead letters are removed entirely, along with until and every notion of expiry. Nothing deletes a job but the operator. A job that keeps failing keeps its place, its failures piling up in its own log behind an exponential backoff. A job with nothing left to do — a one-shot that acted, a schedule out of wakes — is marked done and kept, because deleting it would delete the record of what it did.

Consequences

The job list becomes the place jobs are understood, and it is complete: nothing has been silently removed from it. "Did that reminder fire?" is answered by looking at the reminder. A failure that used to end a job now sits in front of the operator until they decide, which is the right party to decide it.

The cost is that the list grows. A one-shot no longer disappears, so a habit of setting reminders leaves a row per reminder, and clearing them is manual. That is the trade taken deliberately: an accumulating list is a nuisance, and a job deleted before it was read is a lost instruction.

Two guards go with the removal. The circuit breaker stays — it is what stops a billing outage filling every job's log with the same failure. And a job whose session no longer exists is now an ordinary failure on a backoff rather than a deletion, so it stays visible instead of vanishing with the conversation.

This supersedes the dead-letter half of ADR-009 and removes the deadline field that replaced the 24-hour expiry.

ADR-029 · accepted · amends ADR-023

No cost floor on how often a job wakes

Context

A job with no check ran a turn on every wake, so ADR-023 held such a job to a fifteen-minute floor. It was the last rule in the scheduler that refused a request on the system's behalf.

Asked for a stretch reminder every ten minutes, the agent was refused and routed around it in two turns: it created a one-shot whose prompt was "remind them, then schedule the next one ten minutes from now". Same cadence, same model call per wake, plus a schedule call on top — and instead of one legible row the operator got a chain of jobs, each existing for one wake. The floor made the outcome more expensive and less visible than the thing it forbade.

Decision

Remove the floor. Any schedule is accepted. The distinction it was built on is kept where it belongs: a check makes a wake free, the scheduling skill says to reach for one, and a job's schedule, check, and run count sit on the row where the operator can see what it costs.

Consequences

A ten-minute reminder is one job that wakes every ten minutes, which is what was asked for and the cheapest way to do it. scheduleInterval and the floor's error message go with the rule, and the scheduler stops having an opinion about what the operator may want.

The cost is real and now unguarded: a repeating job with a tight cadence and no check calls the model on every wake, and nothing refuses it. The check is that this is visible — on the job, in its run log, and in the session's own cost line — rather than prevented. A guard that is trivially sidestepped by the very agent it constrains was not buying safety; it was buying a worse implementation of the same request.

ADR-030 · accepted · corrects ADR-024

The working-directory boundary is the operating system's, not the tool's

Context

ADR-024 gave each session a working directory and said the isolation was real rather than conventional. It was conventional. The file tools called a helper that refused a path outside the directory; bash could not, because it is a shell and a shell does what it is told. Run exactly as the registry runs it, a shell in one session read another session's file and the OPENROUTER_API_KEY out of .env. Every tool the agent writes for itself would have had the same reach, and the specification said otherwise.

Decision

Confine every tool subprocess and every check command in an OS sandbox: Seatbelt on macOS, bubblewrap on Linux. A tool may read what it needs in order to run, may read and write its own session's directory, and may not touch another session's or the file holding the API key.

No library is adopted. The search for a cross-platform one found none: the Go options are Linux-only, and the ones that do span platforms — Anthropic's own sandbox-runtime among them — are a branch over these same two primitives written in another language. Importing a Node runtime into the container, or a Go library whose non-Linux build silently isolates nothing, both cost more than the hundred lines of branch.

Where neither primitive exists, nothing is enforced and the system says so — at startup, in /status, and on the settings screen. There is no switch to turn it off: a setting whose only use is to disable a boundary is a special case that has to be honoured everywhere the boundary is reasoned about, and the absence of the primitive already covers the only honest reason to be without it.

Consequences

The claim ADR-024 made is now true, and there is a test that would have caught it being false: it drives the real registry and the real bash tool, and asserts the reach fails. On a machine with no sandbox that test asserts the system reports the absence instead, so it never passes by accident.

Two costs. The container needs the bubblewrap package, and bubblewrap needs unprivileged user namespaces, which some runtimes restrict — where it cannot run, the agent says it is not enforcing rather than pretending. And the paths must be resolved before they reach a profile: on macOS /var and /tmp are symlinks into /private, and an unresolved path matches nothing, which looks exactly like a sandbox that is working.

It also closed something that was not noticed until later: neither the tool directory nor the skill directory is writable from inside a tool, so the agent could not install either for itself. ADR-033 settles that in the specification rather than in the profile.

This closed the write half only, and only partly: reads stayed open everywhere but two named paths. ADR-034 replaces that deny-list with an allow-list. A tool still reaches the system over AGENT_URL, which is unauthenticated and will hand it another session's transcript and files. That door is open by design and closing it is a separate decision; what changes here is that the specification no longer claims it is shut.

ADR-031 · accepted

The agent's messages are rendered as markdown, by a renderer that escapes first

Context

The model writes markdown whether or not anything renders it. Shown as source, a turn reads as its own seams — bullet stars, fence lines, pipe tables — and the parts that carry the most information, a table of runs or a block of code, are the parts that read worst. Rendering it means the interface builds HTML out of model output, which is the one thing the transcript had never done.

Decision

Render the assistant's turn as markdown, with a renderer written for this repository (web/markdown.js, about 150 lines) rather than a dependency. It escapes the source first and emits only tags it constructed itself, so nothing arrives as markup; a link is dropped unless it points at http, https, mailto, or a path in this app, and an image renders as a link rather than a fetch of a file the operator never asked for. Nested lists and reference links are not supported and render as their own text.

What the operator typed is not rendered, and neither is a job wake: a wake is the job's stored prompt, and the operator's message is their own words. Rendering either would show them something other than what was said.

Consequences

A dependency would have been shorter to write and longer to hold: a markdown library and a sanitiser are two supply chains, in a project that has none, for a surface this small. The cost is that the renderer is ours to be wrong about — so its escaping, its link scheme check, and its behaviour on a turn still streaming are tested directly, and the wiring is tested through the real renderEntry against a DOM.

Markdown is now the shape of the transcript, so a change to the renderer changes how every past message reads. It is deliberately incomplete rather than partly correct: an unsupported construct stays visible as its source, which is the state the interface was in before this decision.

ADR-032 · accepted

The carried summary is system context, not a user message

Context

Rotation seeded a successor by writing its predecessor's summary into the transcript as a message with role user, prefixed [summary of <id>]. That put words in the operator's mouth in the one slot whose meaning is that the operator is speaking now, and it read worst exactly where it mattered: a job wake fires into a session nobody is watching, and the first thing the model saw there was a user turn the operator never typed.

Decision

The summary travels in the successor's system prompt, as a carried_summary section beside memory and platform. It is held in its own field, separate from the session's own rolling summary, and read from the predecessor before the prompt entry is written — the prompt entry is what every later turn sends, so a summary arriving after it would mean sending one prompt and recording another. Once written it is never rewritten, so it sits inside the cached prefix instead of discarding it on every summariser update.

The text is also written into the carried_over event. The projection drops events, so the append-only transcript keeps the record of what the successor started from without the model paying for it twice.

Consequences

Two summary fields now exist and mean different things: summary is what this session is writing for whoever comes next and is never shown to its own model; carried_summary is what the previous session wrote and is fixed for this one's life. Only the first is editable.

The summary is no longer a line in the message list, so an operator reading the successor's transcript finds it in the prompt entry and in the seeding event rather than inline. That is the same place the rest of the inherited context already lives.

ADR-033 · accepted

The agent does not modify itself

Context

The specification led with an agent that writes its own tools, and said it writes its own skills too. Neither had been true since ADR-030 put every tool subprocess in an OS sandbox: the tool directory and the skill directory are outside every writable path, so a tool creating tools/<name>/ or skills/<name>.md is refused by the kernel. No route on the API writes either — POST /tools/reload registers what is already on disk, and there is no write route for skills at all. The interface could not edit a skill either, though the specification claimed it could.

So the headline capability had been dead for as long as the sandbox had existed, and three documents described it in detail.

Decision

Remove self-modification from the system, rather than restore it. The agent does not write tools and does not write skills. Both are authored by the operator, on the filesystem, with whatever editor they already use. reload_tools stays compiled in and stays callable: it is how a running agent picks up what the operator has just installed.

The writing-tools and writing-skills skills are deleted. A skill exists to tell the model how to do something it can do; instructions for an action the kernel refuses are worse than no instructions, because the model spends a turn discovering that.

The alternative was a rule permitting writes to those two directories. It is a small change to the profile and a large one to the boundary: a tool that can write the tool directory can rewrite bash, and every later tool call in every session runs whatever it left there. Self- modification is the single most consequential thing this system could do, and it was reached by accident of scope rather than chosen. Choosing it deliberately remains open; it is not this decision.

Consequences

The system is meaningfully less autonomous, and the overview, the tool specification, the skill specification, and the model's own persona all now say so. A capability the operator believed in and had never seen work is gone from the description of the system, which is the point: the specification is a claim about behaviour, and one that cannot be exercised is a lie with a citation.

What is left is the part that was doing the work anyway. The agent reaches its limits and says which tool it wants and why. Writing a hundred lines of Python was never the constraint; knowing that the capability is missing is.

ADR-004 reasoned about the blast radius of executables the agent writes and runs. Its conclusion is unchanged for a tool the operator installs — it runs beside the gateway, the scheduler, and the key. What changed is that nothing arrives there without a person putting it there.

ADR-034 · accepted

A tool reads and writes only its own working directory

Context

ADR-030 confined writes and left reads open: the profile allowed file-read* everywhere and then denied two things, the workspace root and the file holding the API key. On Linux the same shape, --ro-bind / /. The stated rule was that a tool may read the system it needs in order to run, which reads like an allow-list. It was a deny-list, and the difference is everything that was never named.

Measured on the machine this was written on, a tool could read ~/.ssh — including the private keys — ~/.config/gh, ~/Documents, and every other repository on the disk. The container deployment hides how bad that is: there, almost nothing else is on the filesystem. On a personal machine, which is where this is meant to run, it is the whole home directory.

Decision

Reads become an allow-list, and the allowed set is the smallest one in which a tool can start and do its job:

  • The runtime — the interpreter, its libraries, and what they load. On macOS that is /usr, /System, /Library, /bin, /sbin, /opt, /dev, /private/etc, /private/var/db, and the root directory itself, which Seatbelt needs in order to resolve any path at all.
  • The tool directory, read-only. A tool must be able to load its own executable and the helper beside it. This is the agent's own program text: identical for every session, and the same file the operator installed.
  • Its own working directory, read and write. This is the only writable place.
  • The database file it was handed, and the two journal files SQLite creates beside it. Narrowed from the whole data directory, which had every session's transcript in it.
  • Whatever the operator names in AGENT_READ_PATHS.

Everything else is denied, including the home directory, the repository the agent is running from, and the file holding the API key — which no longer needs a rule of its own, because it is not in any allowed path. The deny-list is gone; there is nothing left to forget to add to it.

AGENT_READ_PATHS is additive operator configuration, not a switch that turns the boundary off. It exists because a browser is often installed outside the system roots — a Playwright cache under the home directory, or an application bundle — and the alternative to naming it is a read-everywhere default. In a container, where the browser is at /usr/bin/chromium, the variable is unnecessary.

The temporary directory follows the same rule: a tool is given a TMPDIR inside its own working directory rather than the system one, so scratch files are as visible and as confined as everything else it writes. A headless browser is pointed at a profile directory there too.

Consequences

A tool can no longer read a file the operator did not put in the session — not ~/notes.md, not a sibling repository. Files reach a conversation by being uploaded into it. That is a real loss of convenience on a personal machine, and it is the loss that was being paid for by exposing the private keys.

The cost is a profile that can be wrong in a way that looks like a broken tool. A missing runtime path is an Operation not permitted from inside an interpreter, which reads as the tool's fault. Against that: the set was derived by running every supplied tool under the profile, the tools run under it in the test suite, and AGENT_READ_PATHS is the documented repair.

Two things were found by building it. A full browser application bundle does not start under the profile even with its directory readable, while the headless shell does — so the headless shell is what the tools look for first. And SQLite needs its -wal and -shm files named explicitly; allowing only the database file leaves a tool that cannot open its own tables.

ADR-035 · accepted

Tools are written in Go, test-first, in this module

Context

Every supplied tool was a Python script. The reason was self-modification: a tool was something the agent wrote for itself mid-conversation, and an interpreter meant nothing stood between deciding to write one and running it. ADR-033 ended self-modification — tools are written by the operator, on a machine that already has a toolchain — and the reason went with it.

What remained was the cost. A tool runs beside the gateway, the scheduler, the database, and the model API key, with the agent's own privileges, and it was the only part of the system with none of the agent's discipline: no compiler, no go vet, a second language to keep correct, and a separate test runner that task test had to know about. The tools were also the part most likely to be wrong, because they are where the parsing lives.

Decision

A tool is a Go package in this module, at tools/<name>, developed test-first, and it ships eval cases as it always did. go build ./..., go vet ./..., and go test ./... reach every tool without being told they exist, and task build compiles each directory to its own run.

The registry contract does not change and is not narrowed: it executes run, hands it JSON on standard input, and reads JSON from standard output. Any language still satisfies it. This is a rule about how tools are written in this repository, enforced by review rather than by the loader, because a loader that checked would be enforcing a convention the contract does not need.

The plumbing every tool repeated — decoding arguments, emitting a result, calling the API, refusing a path outside the workspace, driving a headless browser — moves to internal/tool. It sits under internal/ rather than tools/ because the registry treats every directory in the tool directory as a tool, and a shared package there would be a permanent load failure.

Consequences

Arguments are structs rather than dictionaries, so a mistyped parameter is a compile error instead of a KeyError at three in the morning. The parsing in web_search and web_fetch is now covered by tests that run in the same command as everything else. One language, one test runner, one task check.

Go's regexp has no lookahead, which the Bing result parser had been using to find where one result ends. It is now explicit block slicing, which is clearer than the pattern it replaces. Go's \s is ASCII-only, so a non-breaking space in a rendered page survived a whitespace collapse that Python's Unicode-aware class had absorbed; it is now normalised deliberately. Both were found by porting the tests first.

Two costs, both real. A tool must be built before it runs, so task test depends on task build:tools and a bare go test ./... on a fresh clone will not find the executables until one build has happened. And a Go tool that links a database driver is several megabytes where a script was two kilobytes — notes is 12 MB. Neither is paid at runtime, and neither touches R4: the agent is not rebuilt and not restarted when a tool changes, which is the property that mattered.

ADR-036 · accepted

The agent changes itself by opening a pull request

Context

ADR-033 removed self-modification and ended by saying that choosing it deliberately remained open. This is that choice. What made the old arrangement wrong was not that the agent wrote code, but where the code landed: a tool wrote tools/<name>/ on the running machine and the next call ran it, with nothing between deciding and executing.

Decision

The agent proposes changes to itself the way a person does, and no further: proposing is the whole of what it can do. That is no surprises applied to the agent's own code — what it is changes only when a person approves the change. It clones this repository into a session's working directory — the one place its tools can write — edits there, pushes a branch, and opens a pull request. A pipeline runs task check on the branch. A person reviews and merges. Merging builds an image and redeploys the server, which is how the change reaches the agent.

The sandbox boundary does not move. The tool directory and the skill directory of the running agent stay unwritable, and no route writes either. What the agent gained is a route out through review, not a route around it.

Three properties make the review real rather than decorative. The pipeline that verifies a branch has no credentials, because a proposed change can rewrite the pipeline. The pipeline that publishes and deploys runs on main only, after a merge. And the agent's credential is scoped to one repository, with contents and pull-request write and no workflow scope, so the most it can do unsupervised is open a pull request nobody has merged.

Consequences

The agent can now improve every part of itself — the loop, the interface, its own tools — and it cannot do any of it quickly. The loop is minutes: push, wait for CI, read the result. That is the intended speed. A change reaching production always passed the same gate the operator's changes pass, and the transcript, the branch, the pull request, and the pipeline run are four independent records of what happened, which is the visibility principle applied to the agent's most consequential capability.

What is given up is the property ADR-033 bought: that the code running is code the operator wrote. It is replaced by a weaker but sufficient one — the code running is code the operator merged. The risk that remains is a reviewer approving a change they did not read, which no mechanism here can prevent.

One property of the result is worth naming, because it was not designed and is worth keeping. There is no code for this. The capability is a three-kilobyte skill, git and gh in the image, and a credential delivered to whichever tool names it: no tool, no route, no branch in the loop, nothing in any package that knows the agent can change itself. It is composition, and the same parts would let the agent work on any other repository. Deleting the skill and the two programs deletes the capability and nothing else — which is the cheapest possible answer to “what if this turns out to be a bad idea”.

The corollary is that nothing in the agent enforces any of it. A skill is advice to a model that already has a shell. Every control that makes this safe is outside the process: the credential's scope, the branch protection, a pull-request pipeline holding no secrets, and the sandbox that keeps a tool out of the running agent's own directories. Where the sandbox does not run, the pipeline is no longer the only way in — see Changing the agent.

ADR-037 · accepted

A tool receives only the environment its manifest names

Context

A tool is a subprocess, and a subprocess inherited the agent's whole environment. That put OPENROUTER_API_KEY in front of every tool ever written, including bash, whose whole purpose is to run commands the model composed — commands that can quote text the model read from a web page. ADR-034 had hidden the file the key is read from and never hid the variable it was read into. Giving the agent a GitHub credential would have added a second secret to the same open channel.

Decision

A tool subprocess is started with an environment built from an allow-list: what any program needs to start at all (PATH, HOME, locale, certificates), the variables the tool contract promises (AGENT_DB, AGENT_URL, AGENT_WORKSPACE, AGENT_SESSION, AGENT_JOB, TMPDIR), and whatever the tool's own manifest names in env. Nothing else is passed, and a named variable that is not set is absent rather than empty.

Consequences

Which tool can reach which credential is now a line in a manifest, visible in the interface beside the tool it belongs to, rather than an accident of process inheritance. The browser tools declare AGENT_BROWSER and the Playwright path, which is how the rule was found to work: they broke the moment the allow-list landed, and declaring what they need fixed them.

The cost is that a tool needing a variable nobody anticipated fails in a way that reads as a bug in the tool. The allow-list is the same trade as the sandbox's, for the same reason: a variable nobody considered is absent rather than present.

ADR-038 · accepted

Deployed as one image behind a password, with the sandbox off

Context

The specification described a container on a tailnet with no login, which is the right shape and was not what was available: a small shared server, already running Dokploy and Traefik, with little memory to spare.

Decision

The agent runs as a Dokploy Compose application from an image built by CI, never on the host: there is not enough memory there to compile Go. It publishes no host port; Traefik routes to it over the internal network and a Basic Auth middleware puts one password in front of it, over a Let's Encrypt certificate. Transcripts and session working directories are named volumes, so a redeploy replaces the process and keeps the conversation.

Two acceptance criteria of the architecture are suspended rather than quietly dropped. The container is reachable from outside a tailnet, protected by a password instead. And the tool sandbox does not run: Ubuntu 24.04 blocks unprivileged user namespaces for containers, bubblewrap needs one, and the only container configuration that restores it is --privileged, which is a worse trade on a host that runs anything else. Both are suspensions to be lifted, not properties of the design.

Consequences

The agent is reachable from any network, which is what makes a phone useful without a VPN, and the whole of its access control is one shared secret in front of an interface that runs shell commands. In production a tool can read every session's files and the agent's own directory; the interface says NOT ENFORCED on the panel that reports it, which is the visibility principle doing the only thing it can do about a boundary that is off.

A headless browser does not fit in the memory available, so web_fetch retrieves pages over HTTP and a page assembled by scripts reads as empty. That is a hardware problem, and naming it here keeps it from being rediscovered as a bug.
