Architecture

One process, one container, one user.

Components

ComponentResponsibility
GatewayServes the HTTP API, the web UI, and a WebSocket stream. The only network surface.
Agent loopAssembles a request from a session, calls the model, dispatches tool calls, appends results, repeats until the model stops calling tools.
SchedulerTicks once per second. Fires due jobs into their sessions. Writes each job's run log and owns the circuit breaker.
Tool registryScans the tool directory, validates manifests, exposes schemas to the model, executes tools as subprocesses.
StoreSQLite for structured state and full-text search. JSONL files for transcripts.

All five run in one process. There is no message broker, no worker pool, and no inter-service protocol.

What belongs in the core

The five components above are the core. They are compiled in because each of them owns state that outlives a single call: the loop owns the turn, the scheduler owns time, the store owns the transcript, the gateway owns the socket, the registry owns what tools exist.

Everything the model can invoke is a tool on disk. A tool that needs the system asks for it over the HTTP API, the same one the interface uses. Nothing reaches into the process.

Compiled inWhy it cannot be a tool
reload_toolsIt is the registry's own control surface. A tool that decides which tools exist cannot depend on that decision having already been made.

That is the whole list. A capability is core only when running it outside the process would not work, not when running it inside would be faster or tidier.

The cost is real. A tool call is a subprocess and a local HTTP round trip rather than a function call, and it can now fail from exec or a socket rather than only from bad arguments. The failure shape is the same either way — an error result the model can read — so the turn degrades identically. What is bought is that every capability can be read and replaced without a toolchain, by the operator and by the agent.

Acceptance criteria

  • Every tool the model can call is a directory under the tool directory, except those this table names.
  • A tool is given the API base URL, its session, and its job, and needs nothing else to reach the system.
  • Removing a tool directory removes the capability, with no code change.
  • No core component calls a tool's implementation directly.

Storage

Transcripts are JSONL files on disk, one per session, appended to and never rewritten. They are the source of truth.

SQLite holds everything else: sessions metadata, jobs and their run logs, memory, tool state, and a full-text index over transcript entries. Both the metadata and the index are derived from the JSONL files and can be rebuilt from them.

Files are neither. Each session owns a directory under the workspace, which is where its tools run and its uploads land; it is copied when the session is continued and removed when the session is deleted. A session and its directory together are what an export carries.

Why both. A transcript is an append-only log and belongs in a file. Everything else is queried, filtered, and joined, and belongs in a table. Rebuildability means a corrupt database costs a restart, not data.

Acceptance criteria

  • Deleting the SQLite file and restarting reconstructs all session metadata and search indexes from the JSONL transcripts.
  • SQLite runs in WAL mode.
  • No transcript entry is ever modified or deleted once written.
  • Tool tables are namespaced by a prefix declared in the tool's manifest.
  • Each session's files live in a directory of its own under the workspace, and are deleted with it.

Configuration

Settings come from the environment. At startup the agent also reads a file of KEY=VALUE lines from the working directory and fills in anything the environment does not already define.

The file exists because the alternative is a shell that has to be prepared correctly before every start. A setting that lives only in a shell is lost on the next terminal, the next reboot, and the next person to run the thing — and the one setting that must always be present is the model API key, whose absence turns every scheduled job into a failure hours after the mistake was made.

The environment wins. A variable already set overrides the file rather than the other way round. A file that shadowed an explicit setting would make a one-off override silently ineffective, which is worse than having no file at all.

The file is optional and a missing one is not an error: every setting has a default, and the agent reports what it read rather than what it expected. It holds a credential, so it is excluded from version control and the agent says so at startup if other users can read it.

Acceptance criteria

  • The agent starts correctly configured with no environment prepared beyond the file.
  • A variable set in the environment takes precedence over the same variable in the file.
  • A missing file is not an error and is not reported as one.
  • Startup reports how many settings were read and from where, and never their values.
  • Startup warns when the file is readable by users other than its owner.
  • No credential is written to a transcript, to the database, or to the log.

Model access

All model calls go to OpenRouter over its OpenAI-compatible API. The model is selected per session and can be changed mid-session.

Three OpenRouter endpoints are consumed beyond inference:

EndpointUsed for
/modelsPopulating the model picker, context-window sizes, and per-token prices. Cached, refreshed daily. Models are filtered to those whose supported_parameters include tools.
/keyRemaining credit and usage totals shown in the UI.
/chat/completionsInference, streamed.

Retrying a model call

A call can fail because the upstream was briefly unreachable or because the account cannot make it at all, and only the first is worth trying again. A blip loses a whole wake otherwise: the run fails, the reminder never arrives, and the operator finds out by not being reminded.

An inference call is attempted up to three times. A rate limit, a 5xx, a timeout, and a broken connection are retried, with the wait doubling from two seconds and a Retry-After honoured when the upstream sends one. An exhausted account, a rejected key, a withdrawn model, and a malformed request are not: they would fail identically and would delay the breaker that should trip.

Retrying stops the moment the answer begins arriving. The deltas are already on the operator's screen and counted against the session, so a second attempt would say the first half twice; a stream that breaks mid-answer is reported as a failure instead. The whole call, retries included, is bounded at fifteen minutes, so one turn cannot hold a job that wakes every twenty.

Acceptance criteria

  • A rate limit or a 5xx is retried; the call succeeds if a later attempt does.
  • An exhausted account, a rejected key, a withdrawn model, or a malformed request is attempted once.
  • A failure after the first token of the answer is not retried, and what was streamed is streamed once.
  • Attempts are bounded, and the error reported after the last one carries the failure that caused it.
  • A cancelled turn stops without working through its remaining attempts.

Prompt caching

Caching is not free. A cache write costs more than an ordinary read — 1.25x for a five-minute lifetime, 2x for an hour — so a prefix that is written and then read only once or twice costs more than not caching at all. Break-even is around three calls within the lifetime.

Long-lived sessions frequently sit below that. A session whose only job uses a deterministic check makes no model calls at all between firings, so caching it would double the cost of each isolated call.

The cache is therefore requested only when another call is expected before it expires.

Acceptance criteria

  • For providers requiring explicit cache breakpoints, the request carries a cache marker at the end of the stable prefix.
  • A cache write is requested only when a further call is expected within its lifetime: the user turned recently, or the session has a model-invoking job due sooner than the lifetime.
  • Active conversation requests the five-minute lifetime; a session with a frequent model-invoking job requests the hour.
  • An isolated call on an idle session requests no cache write.
  • Reported cached-token counts and cache discount are recorded per call and surfaced in the UI.
  • Providers that cache automatically receive no cache markers.

Deployment surface

HTTPS, real certificate"}} PH --> TS LP --> TS TS --> GW["Gateway :8080"] GW --> OR["OpenRouter"]

The container publishes no ports to the public internet. Tailscale Serve terminates HTTPS with a certificate valid for the tailnet hostname.

What is deployed today does not do this, and ADR-038 records why. The agent runs as a Dokploy Compose application on a shared box; Traefik terminates HTTPS with a Let's Encrypt certificate for a public hostname and puts a Basic Auth middleware in front of the agent. The container still publishes no host port — only Traefik reaches it, over the internal network — but the hostname is public and one password is the whole of the access control. The tailnet remains the intended answer; the password is what stands in for it.

The image is built by CI and pulled by tag, never built on the server, which has neither the memory nor a toolchain. Transcripts and session working directories are named volumes, so a redeploy replaces the process and keeps every conversation, job, and file.

Nothing reaches the phone unless the phone asks. There is no push service and no outbound notification path: the operator reads what happened by opening the interface, which means the phone must be on the tailnet to learn anything at all.

Acceptance criteria

  • The container exposes no port of its own; everything reaching it arrives through the proxy in front of it.
  • Nothing reaches the interface without either being on the tailnet or presenting the credential the proxy requires.
  • The web UI is served over HTTPS with a certificate the browser trusts without exception.
  • A redeploy replaces the process and keeps every session, job, memory item, and uploaded file.
  • The container reports whether the process inside it is answering, using the agent's own binary rather than a second program carried for the purpose.
  • A confinement mechanism is claimed only after it has been shown to run on this machine; one that is installed but refused reports as not enforced, with the refusal as its reason.
  • The deployed image is built from a commit on the default branch and is tagged with it, so what is running can be named.
  • The system makes no outbound connection to any push service.
  • A phone off the tailnet fails visibly rather than showing a blank screen.

Changing the agent

The agent proposes changes to itself (ADR-036), which is the second half of no surprises: the agent you are talking to tomorrow is the one you approved today. It is worth being exact about what that consists of, because it is not a feature and there is no code for it.

WhatIs
skills/changing-yourself.mdThe procedure, as prose: clone into this session's working directory, branch, edit, push, open a pull request, read what the pipeline says. About three kilobytes.
git and gh in the imageThe two programs that procedure needs. Everything else it uses — the shell, the file tools, the network — is there for every other task too.
GH_TOKEN, AGENT_REPOA credential and an address, delivered to a tool that names them in its manifest (ADR-037).

That is the whole of it. No package in the agent knows this capability exists: no tool, no route on the API, no branch in the loop. It is composition — a shell, a network, and a document — and the same three parts would let the agent work on any other repository just as well.

Nothing in the agent enforces the procedure. A skill is advice to a model that already has a shell; it shapes what the agent does and constrains nothing. Every control that makes this safe sits outside the process: the scope of the credential, the branch protection that refuses a merge without a green pipeline, the pipeline that holds no secrets on a pull request, and the sandbox that keeps a tool out of the agent's own directories. An agent that ignores its skill entirely still cannot merge; an agent on a host where the sandbox does not run can write the tool directory of the copy that is running, and the pipeline stops being the only way in.

Acceptance criteria

  • No source file in the agent, its tools, or its commands refers to the credential or the repository the agent proposes changes to. The capability is a skill, two programs, and the tool environment; a code path for it is a defect.
  • Removing the skill and the two programs removes the capability, and nothing else changes.
  • The agent cannot write the tool directory or the skill directory of the running process, so a change reaches the running agent only by being merged and deployed.
  • What constrains the agent is stated where the capability is described: the credential's scope, the branch protection, a pipeline without secrets, and the sandbox.

Process boundaries

The agent, its tools, and the gateway run as one user in one container. A tool has the privileges of that user, with one boundary the operating system enforces: the session's own working directory.

Every tool subprocess, and every check command, is launched inside a sandbox. There is no cross-platform library for this — everything that claims to be one branches on the platform — so this does too, over the two primitives that need no privileges: Seatbelt (sandbox-exec) on macOS and bubblewrap (bwrap) on Linux.

A tool reads and writes its own session's working directory, and nothing else. Both halves are an allow-list, so a path that was never considered is denied rather than permitted (ADR-034). Four things are allowed beyond the working directory, and each is what lets a tool run at all rather than a convenience:

PathAccessWhy
The runtime — /usr, /System, /Library, /bin, /sbin, /opt, /dev, /private/etc, /private/var/db, and / itselfreadThe interpreter and everything it loads. Without it no tool starts.
The tool directoryreadA tool loads its own executable and the helper beside it. The agent's own program text, not the operator's data.
The database file and its -wal and -shm journalsread, writeA tool is handed AGENT_DB on purpose and may keep its own tables. Narrowed from the data directory, which holds every session's transcript.
AGENT_READ_PATHSreadNamed by the operator. A browser installed outside the system roots is the case it exists for.

Everything else is denied: the home directory, the repository the agent runs from, another session's working directory, the skill directory, and the file holding the model API key — which needs no rule of its own, because it is in no allowed path. The temporary directory is inside the session's own working directory too, so a tool's scratch files are as visible and as confined as everything else it writes.

The tool directory and the skill directory are readable and never writable. The agent does not install tools and does not write skills; the operator does, on the filesystem (ADR-033).

Where neither primitive is available the system enforces nothing, and says so: at startup, in /status, and on the settings screen. A sandbox that silently does nothing is worse than one that is plainly absent, because the first is trusted. There is no setting that disables it: the only reason to run unconfined is that the platform offers nothing to confine with, and that case already reports itself. AGENT_READ_PATHS is not that setting — it only adds, and what it adds is visible in /status.

What this is not: a tool still holds the agent's other privileges. It is given AGENT_DB and reaches the system over AGENT_URL, and that API is unauthenticated — a tool can ask it for another session's transcript or files. The filesystem boundary is real; the API is deliberately open, and closing it is a separate decision.

Acceptance criteria

  • A tool can read and write its own session's working directory, and can run the interpreters it needs.
  • A tool cannot read or write any other path: not another session's directory, not the operator's home directory, not the repository the agent runs from, and not the file holding the API key.
  • A tool cannot write the tool directory or the skill directory, and is refused by the operating system rather than by its own good manners.
  • A tool may read and write the database file it is handed, and no other file in the data directory.
  • A path named in AGENT_READ_PATHS is readable and still not writable, and the paths in force are visible in /status.
  • A check command is confined exactly as a tool is.
  • A confined tool can drive a headless browser, so the web tools work under the sandbox rather than only outside it.
  • When nothing is enforcing, the system says so at startup, in /status, and in the interface.
  • Aside from the filesystem boundary, a tool runs with the agent's privileges, including its access to the unauthenticated API.
  • Nothing recovers automatically from a tool that damages the system; repair is manual, and the specification says so rather than implying otherwise.

The tradeoff is recorded in ADR-004.
