Tools

A tool is a directory containing an executable and a manifest. Nothing more.

You write one, and the agent loads it. Because a tool is a directory on disk rather than compiled into the agent, adding one restarts nothing: the agent keeps running and picks the tool up on a reload.

Layout

tools/deploys/
  manifest.json     required — identity, parameter schema, database prefix
  main.go           required — the tool, in Go, with the agent's own discipline
  main_test.go      required where there is logic to test — written first
  run               required — the compiled executable, built from this directory
  eval.json         required — the cases a real model is put through
  schema.sql        optional — tables, applied on load
  ui/panel.js       optional — an interface panel for this tool's data

The tools that ship

Each has a page of its own: what it does, what it refuses, how it fails, and the criteria that hold it to that. A manifest states a tool's interface and is the only statement of it — the pages below do not repeat the parameter schema, because two descriptions of one interface is one of them going stale. What a page carries is everything a manifest cannot: the behaviour, the boundary, and the reasoning.

ToolFor
bashRun a shell command in the session's working directory.
clockThe current date and time, in UTC and in the operator's zone.
editReplace an exact string in a workspace file.
memoryWrite, revise, or remove what the agent carries between conversations.
notesShort freeform notes that outlive a conversation.
readRead a file from the session's working directory.
scheduleCreate, list, edit, and delete the jobs that make future work visible.
session_searchFull-text search across transcripts.
skill_readLoad the full text of a skill.
web_browseOpen a URL in a browser and return the page's text.
web_searchSearch the web and return titles, URLs, and snippets.
writeCreate or replace a file in the session's working directory.
A tool without a page is not finished. The manifest tells the model what the tool takes; the page tells the operator what it does and the test suite what to hold it to. A capability whose failure modes are written down nowhere is one whose behaviour is discovered in production.

Acceptance criteria

  • Every directory under tools/ has a specification page, and every page names a tool that exists.
  • A page states what the tool refuses and how it fails, not only what it does.
  • A page carries acceptance criteria, and each is discharged by a test that runs the tool as a subprocess.
  • No page restates the manifest's parameter schema; the manifest is the single statement of the interface.

Tools are written the way the agent is

A tool is Go, in this module, developed test-first, and it ships eval cases. The registry executes run and does not care what produced it — the contract below is a subprocess, JSON in and JSON out, which any language satisfies. This is a rule about how tools are written here, not a limit the code enforces.

The rule exists because the argument for a scripting language died with self-modification. A tool used to be something the agent wrote at three in the morning, where an interpreter meant no build step between deciding and running. ADR-033 ended that: tools are written by the operator, at a keyboard, with a toolchain already open. What is left is a program that runs beside the scheduler and the database, holds the same privileges, and had none of the discipline applied to everything around it — no compiler, no vet, a separate test runner, and a second language to keep correct. The reasoning is in ADR-035.

So a tool is held to what the agent is held to:

WhatMeans
Go, in this moduletools/<name> is package main. go build ./..., go vet ./..., and go test ./... reach it without being told.
Test-firstBehaviour is captured by a failing test before it is written. Logic worth having is worth separating from the subprocess plumbing so it can be tested directly.
Evalseval.json, as before. A test cannot tell whether a description reads correctly to a model; only a model can.
End to endA criterion is discharged by a test that runs the tool as an actual subprocess, through the registry, inside the sandbox.
Shared helperinternal/tool carries the subprocess contract, the API client, the workspace boundary, and the headless browser. A tool that reimplements one of these is a tool that will disagree with the others.
The build is not the agent's. task build compiles each tool directory to its own run. Changing a tool means rebuilding that tool and reloading; it never means rebuilding or restarting the agent, which is the property R4 is actually about. The binaries are not in the repository.

Manifest

{
  "name": "deploys",
  "description": "Query deployment status and history.",
  "db_prefix": "deploys_",
  "timeout_seconds": 30,
  "reads": ["/proc"],
  "parameters": {
    "type": "object",
    "properties": {
      "action": { "type": "string", "enum": ["status", "history"] },
      "service": { "type": "string" }
    },
    "required": ["action"]
  }
}

Acceptance criteria

  • description is a single sentence.
  • db_prefix is unique across tools and every table the tool creates begins with it.
  • reads is optional and names the paths this tool may read beyond the runtime every tool gets. A tool that asks for nothing reads the runtime, its own directory, and its session's working directory. Granting the union of what any tool might need would give every tool the widest boundary any of them asks for.
  • parameters is a valid JSON Schema object and is exposed verbatim to the model.
  • A tool directory without eval.json is reported by the test run, so a capability cannot be added without evidence that a model can use it.
  • A manifest missing a required field prevents that tool from loading and does not affect other tools.
  • Every tool directory is a Go package in this module, and go vet ./... and go test ./... cover it without a separate runner.
  • Building or changing a tool requires no rebuild and no restart of the agent.

Execution

A tool call runs the executable as a subprocess. Parameters arrive as JSON on standard input; the result is JSON on standard output. The environment carries what a tool needs to reach the rest of the system: the database path, the tool's table prefix, the API base URL, and the session and job the call belongs to.

It carries nothing else. A subprocess used to inherit the agent's whole environment, which handed the model API key to every tool including the one that runs shell commands the model wrote. The environment is now built from an allow-list — what any program needs to start, what the table below promises, and whatever the calling session was granted by name (ADR-037, ADR-045). A variable nobody granted is absent, and a granted variable that is not set stays absent rather than arriving empty.

VariableHolds
AGENT_DBPath to the SQLite database.
AGENT_DB_PREFIXThe tool's table prefix.
AGENT_URLBase URL of the HTTP API, the same one the interface uses.
AGENT_SESSIONThe session this call belongs to.
AGENT_JOBThe job this call belongs to, empty when the user asked directly.
TMPDIRA directory inside the session's own working directory. A tool's scratch files are as confined and as visible as everything else it writes.

Beyond that list, and the handful any program needs to start at all — PATH, HOME, the locale, the certificate paths — a tool receives a variable only because the conversation it is running in was granted it by name (ADR-045). A grant belongs to a session, not to a tool: a credential is something an operator hands to one conversation, where a manifest could only say every session or none of them, for the life of the deployment. The OPENROUTER_API_KEY is the one name no grant can carry, because it is the variable the whole allow-list exists to keep out.

stdin   {"action": "status", "service": "web"}
stdout  {"ok": true, "content": "web: deployed 12m ago, healthy"}
        {"ok": false, "error": "service 'web' not found"}

A tool that fails returns an error the model can read and act on. A tool that crashes, times out, or writes unparseable output is reported to the model in the same shape, so a broken tool degrades the turn rather than the process.

Acceptance criteria

  • A tool exceeding its timeout is killed and reported as an error result.
  • A tool can reach every capability the interface can, through AGENT_URL, without a private hook into the process.
  • A tool crashing or emitting invalid JSON produces an error result, not a failed turn.
  • Standard error is captured and stored with the result, not shown to the model.
  • A tool subprocess receives only the variables above and the ones its calling session was granted; the model API key and every other variable of the agent's environment are absent.
  • A variable a manifest names is passed only to that tool, and only when it is set.
  • Tool results are recorded as transcript entries.

Loading

Tools load at start and on explicit request — the interface's button, POST /tools/reload, or the agent's own reload_tools call, which is how a running session picks up what the operator has just installed. There is no directory watcher, because a tool appearing halfway through being copied into place is worse than one appearing a moment later.

A reload does not reach the session that asked for it. That session's prompt defines exactly the tools it had, and a session's tools are fixed for its life. A tool installed now is a tool a new session has. An existing conversation reaches it by forking, which copies the conversation into a session built with the new tool in it.

This is unlike memory, which a compaction refreshes into the running conversation. Memory is text the model reads; a tool is a definition the model programmes against, and changing the callable set mid-conversation is the thing ADR-019 removed.

Loading validates before registering. A tool is registered only if its manifest parses, its schema is valid, its executable is executable, its database prefix is unused, and a trial invocation returns parseable output.

Acceptance criteria

  • A reload registers a validated tool without restarting, and it appears in the prompt of every session started after it.
  • A newly registered tool is not callable in a session already running, whose prompt was written without it.
  • The session that asked for the reload records what was added, as a visible entry the model is not sent.
  • A tool failing validation is not registered, and the reason is returned to the caller.
  • A failed reload leaves previously loaded tools working.
  • Reloading applies any new schema.sql exactly once per tool version.

Evals

A tool's description and parameters are the surface a model programmes against, and nothing deterministic tests them. A schema the system handles perfectly can still be one no model reads correctly — the failure is real, it costs a round trip or a wrong action every time, and every test that stubs the model out is blind to it.

So every tool directory carries an eval.json: requests put to a real model with that tool available, and what its tool use has to look like.

{
  "cases": [
    {
      "name": "relative reminder lands in one call, no retry",
      "prompt": "Remind me to stretch in ten minutes.",
      "tools": ["schedule", "clock"],
      "expect": {
        "tool": "schedule",
        "args": { "action": "create", "after_acting": "stop" },
        "args_match": { "schedule": "^10m$" },
        "clean": true
      }
    }
  ]
}

A case runs in a throwaway session against the whole system: the real store, the real tool as a subprocess, and the API served on its own port so the tool reaches the same system it is being tested in. Only the work's destination is temporary.

clean is the assertion that matters most. It requires that the tool under test never returned an error — that the model got the shape right first time rather than learning it from a rejection. It is scoped to that tool: a shell probe that exits non-zero is a legitimate answer, and counting it would punish the agent for testing a check before scheduling it.

An eval is not a test. It drives a real model, so it costs money and its result varies between runs. It is a command, not part of the test run, and it is read as evidence rather than as a gate. What is a test is the requirement that every tool has one, which is why a tool shipped without eval cases fails the ordinary test run.

The model is configurable and defaults to a free one, because an eval that is expensive to run is an eval nobody runs. A failing case is usually a defect in the description rather than in the model, and is fixed there.

Acceptance criteria

  • Every tool directory contains eval.json with at least one case, and the test run fails when one does not.
  • An eval case runs against the real store, the real tool subprocess, and an API the tool can reach, in a session discarded afterwards.
  • Evals never run as part of the test suite, and never require an API key to run the suite.
  • The eval model is configurable and defaults to one that is free to run.
  • A case can require that the tool under test was never rejected during the turn.
  • A case can seed files into its own working directory, so a tool that operates on files is evaluated against files that exist rather than against a prompt that claims they do.
  • A provider rate limit is retried rather than reported as a failed case.

Who writes a tool

The operator does. A tool is a directory the person running the agent creates on the filesystem, with whatever editor they already use. The agent does not write tools, and the specification no longer says it does — the reasoning, including why the sandbox was not opened up instead, is in ADR-033.

The boundary is the operating system's, not a convention. The tool directory is readable by a tool — it has to be, or nothing would start — and writable by none. A tool that tries to create tools/<name>/ is refused by the kernel, and no route on the API writes one: POST /tools/reload registers what is already on disk.

What the agent does instead is say which tool it wants and why, at the point it runs out of capability. That is the part of the job that needs the conversation; the hundred lines of Python were never the constraint.

Acceptance criteria

  • A tool subprocess cannot create or modify anything in the tool directory, and is refused by the operating system rather than by its own good manners.
  • A request for a capability that does not exist is answered by naming the missing tool, not by attempting to install one.
  • A tool the operator installs appears in the interface after a reload, marked as new, with its manifest readable.
  • A tool outside a session's set is absent from that session's prompt, so there is nothing to refuse.
  • Deleting a tool removes it from the model's schema list and leaves its tables intact.

Interface plugins

A tool that stores data may ship a panel to display it. The panel is a JavaScript module the web interface loads and mounts under that tool's name. A memory tool shows what it remembers; a scheduler tool shows its jobs.

Acceptance criteria

  • A tool with a panel gains a navigable section in the interface without changes to the interface itself.
  • A tool without a panel is still fully usable.
  • A panel that fails to load reports the failure and does not prevent the rest of the interface from working.
  • Panels read tool data through the API, not by querying the database directly.

The supplied tools

The agent ships with a set of tools in the tool directory. They are ordinary tool directories with no privileges of their own: readable, editable, and removable without a rebuild, exactly like one you write yourself. Deleting one removes the capability and nothing else.

Searching the web

A search results page is assembled by scripts, so fetching its HTML returns a shell with no results in it. web_search therefore drives the headless browser the image installs, at the one path it installs it to, and reads the results out of the rendered DOM.

The browser is used as it is delivered. Nothing disguises the request, and an engine that declines to serve an automated query is reported as having declined — naming the phrase it used — rather than worked around or reported as a query that found nothing. The two are different answers and only one of them means the query was wrong.

The dependency sits in the tool. A browser is a large thing to install for one capability. Because the capability is a directory rather than compiled in, the cost falls on whoever wants search: delete the directory and the dependency is gone, with no rebuild. This is the shape R4 is for.

Acceptance criteria

  • A search returns result titles, absolute URLs, and snippets, with click-tracking redirects resolved to the page they point at.
  • An engine declining to serve the query is reported as a refusal, distinct from a query with no results.
  • No request is disguised and no bot check is answered or evaded.
  • With no browser at the path the image installs it, the tool fails naming that path, and every other tool keeps working.

Fetching a page

Most of the web arrives empty. The HTML a server sends is a shell, and the text a person reads is written into it by scripts once the page is running. Retrieving the bytes therefore answers a different question from the one the model asked. web_browse loads the URL in the same headless browser web_search uses — the one the image installs, at one path — lets the scripts run, and reads the settled DOM.

Text is recovered from that DOM rather than from the source, because a rendered DOM has had its source whitespace squeezed out: the tags that end a line on screen are the only remaining evidence of where one thing ends and the next begins. A body the browser cannot render as a document — JSON, plain text — is returned exactly as it was served, since the point of fetching an API is its bytes.

The browser is required, and there is one of it: the image installs chromium and CI installs the same package, so the path is fixed and nothing is searched for (ADR-044). An image without it is broken rather than degraded, and the tool says so. The tool used to fall back to a plain HTTP GET, which returned a page needing its scripts as the shell it ships as — indistinguishable, to whoever asked, from a page that simply says little. A plain fetch is a different thing to want, and when it is wanted it belongs in a tool of its own that the model chooses on purpose.

As in search, the browser is used as it is delivered: nothing disguises the request, and a site that declines to serve it is not worked around.

Acceptance criteria

  • A page whose text is written by its scripts is returned with that text in it, and without the placeholder it replaced.
  • A JSON or plain-text body is returned verbatim, not as flattened prose.
  • The tool renders every page it returns; there is no unrendered path, so a thin page means a thin page.
  • With no browser at the path the image installs it, the tool fails naming that path rather than returning something unrendered.

One tool is compiled in, for the reason given in Architecture: reload_tools, which is the registry's own control surface.
