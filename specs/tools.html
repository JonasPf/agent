Tools

A tool is a directory containing an executable and a manifest. Nothing more.

The agent can write one, and does so when the capability it needs does not exist. Because a tool is a file on disk rather than compiled-in code, adding one requires no restart and no rebuild.

Layout

tools/deploys/
  manifest.json     required — identity, parameter schema, database prefix
  run               required — executable, any language
  schema.sql        optional — tables, applied on load
  ui/panel.js       optional — an interface panel for this tool's data

Manifest

{
  "name": "deploys",
  "description": "Query deployment status and history.",
  "db_prefix": "deploys_",
  "timeout_seconds": 30,
  "parameters": {
    "type": "object",
    "properties": {
      "action": { "type": "string", "enum": ["status", "history"] },
      "service": { "type": "string" }
    },
    "required": ["action"]
  }
}

Acceptance criteria

  • description is a single sentence.
  • db_prefix is unique across tools and every table the tool creates begins with it.
  • parameters is a valid JSON Schema object and is exposed verbatim to the model.
  • A manifest missing a required field prevents that tool from loading and does not affect other tools.

Execution

A tool call runs the executable as a subprocess. Parameters arrive as JSON on standard input; the result is JSON on standard output. Two environment variables are provided: the database path and the tool's table prefix.

stdin   {"action": "status", "service": "web"}
stdout  {"ok": true, "content": "web: deployed 12m ago, healthy"}
        {"ok": false, "error": "service 'web' not found"}

A tool that fails returns an error the model can read and act on. A tool that crashes, times out, or writes unparseable output is reported to the model in the same shape, so a broken tool degrades the turn rather than the process.

Acceptance criteria

  • A tool exceeding its timeout is killed and reported as an error result.
  • A tool crashing or emitting invalid JSON produces an error result, not a failed turn.
  • Standard error is captured and stored with the result, not shown to the model.
  • Tool results are recorded as transcript entries.

Loading

Tools load at start and on explicit request. The agent calls a reload after writing one; there is no directory watcher, because a tool appearing halfway through being written is worse than one appearing a moment later.

Loading validates before registering. A tool is registered only if its manifest parses, its schema is valid, its executable is executable, its database prefix is unused, and a trial invocation returns parseable output.

Acceptance criteria

  • A reload makes a newly written tool callable within the same session by appending its definition to the transcript, without restarting and without invalidating the cached prefix.
  • A tool failing validation is not registered, and the reason is returned to the caller.
  • A failed reload leaves previously loaded tools working.
  • A successful reload commits the tool directory to version control.
  • Reloading applies any new schema.sql exactly once per tool version.

Self-authoring

Writing a tool is an ordinary task the agent performs with its file and shell tools, guided by a skill that describes this convention. It is not a special mechanism.

Acceptance criteria

  • A request for a capability that does not exist results in a tool being written, loaded, and used in the same conversation.
  • A newly created tool appears in the interface, marked as new, with its manifest readable.
  • A disabled tool returns an error result naming the session it is disabled in, rather than being absent.
  • Deleting a tool removes it from the model's schema list and leaves its tables intact.

Interface plugins

A tool that stores data may ship a panel to display it. The panel is a JavaScript module the web interface loads and mounts under that tool's name. A memory tool shows what it remembers; a scheduler tool shows its jobs.

Acceptance criteria

  • A tool with a panel gains a navigable section in the interface without changes to the interface itself.
  • A tool without a panel is still fully usable.
  • A panel that fails to load reports the failure and does not prevent the rest of the interface from working.
  • Panels read tool data through the API, not by querying the database directly.
