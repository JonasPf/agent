Skills

A skill is a document that teaches the agent how to do one thing. It is prose, not code.

Skills are how the agent accumulates competence. A tool adds a capability; a skill adds judgement about when and how to use one.

Form

skills/scheduling.md

---
name: scheduling
description: Use before creating or changing a job — how to turn a request for later into one.
---

A request for later is either a time or a condition…

A skill that needs more than one file is a folder: SKILL.md, whose front matter names the skill exactly as a single file's does, and the files beside it — a checklist, a table, a longer example — in folders of their own if it likes. The index carries the folder as one line. skill_read returns SKILL.md with the other files' paths after it, and reads any one of them when the procedure says it is needed (ADR-069).

skills/trip-planning/SKILL.md
skills/trip-planning/packing.md
skills/trip-planning/ref/checklist.csv

A skill a conversation should set out to use, rather than find in every prompt, adds default: off to its frontmatter. A session that did not choose its skills then leaves it out; a session that lists its skills has exactly the ones it lists (ADR-050). No shipped skill does: the two that did, for changing code, were never read, because no conversation turned them on, and were removed (ADR-064). Off remains a choice for a skill the operator writes.

Progressive disclosure

Only the name and description of each skill appear in the system prompt. The agent loads a skill's full text with skill_read when the work in front of it is work the skill covers.

Left to judge relevance from a list, it mostly did not: a skill was in front of the model in under a third of the turns it covered. So the index opens with the rule — read the skill before starting the work, and again whenever its text is no longer there, because compaction folds a skill away like any other turn — and a description says when to use a skill before it says what is in it. "Use when the operator asks you to remember, note, or keep track of anything…" is a trigger a model can match a request against; "How to keep a record…" is a summary it has to infer one from.

This is what allows the collection to grow. Twenty skills cost a few hundred characters of context rather than twenty documents' worth.

Acceptance criteria

  • The system prompt lists the name and description of every skill enabled for the session, and no skill's body.
  • A skill's description is a single line.
  • The index opens by saying to read a skill with skill_read before the work it covers, and again after compaction; an empty index says only that there are none.
  • Every shipped skill's description begins with when to use it.
  • Reading a skill is a tool call visible in the transcript.
  • Adding a skill requires no restart.
  • A skill with malformed frontmatter is skipped, and the failure is visible in the interface.
  • A skill whose frontmatter says default: off is absent from the index of a session that did not choose its skills, and present in one that chose it.
  • A default that is neither on nor off is malformed frontmatter.
  • A skill that is a folder is named by its SKILL.md's front matter and indexed as one line, with nothing from its other files.
  • A folder without a SKILL.md, or holding a file that is not text, is skipped, and the failure names it.
  • Hidden files in a skill's folder are not part of the skill.
  • The skill list says, for each skill, whether it is on by default.
  • Every shipped skill is on by default.

Who writes a skill

The operator does — in the interface, or on the filesystem. A skill is a Markdown file the person running the agent writes. The agent reads skills and does not write them (ADR-033, ADR-053).

There are two roots. Skills that ship in the image are read-only: the image is replaced on every deployment, so an edit there would be lost at the next upgrade. Skills the operator writes live beside the data, which is the one directory a deployment keeps, and are created, edited, and deleted on the Skills panel.

Neither root is writable by a tool — neither is in any path the sandbox allows a tool to write — so the boundary is the operating system's, not the agent's good manners. The interface is the operator, and writes; the agent reads.

A skill the operator writes may not take the name of one that ships: a name is an identifier, and two skills answering to one would make the index a lie about what skill_read returns. The collision is refused and said out loud.

What survives from before is the reason skills existed: a lesson worth keeping is worth writing down, and prose is the safe form for it. When the agent works something out that the next attempt should start from, it says so, and the operator decides whether it becomes a skill.

Acceptance criteria

  • A tool subprocess cannot create, modify, or delete anything in either skill directory, and is refused by the operating system rather than by its own good manners.
  • Skills are read from files on disk, not from the database, and a skill added by the operator is available to sessions started after it.
  • Every skill is readable in the interface.
  • A skill outside a session's set is absent from its index, and reading it by name reports no such skill.
  • The interface creates, edits, and deletes a skill, and what it writes is a file on disk that a restart reads back.
  • A skill written through the interface is stored outside the image, so replacing the image keeps it.
  • A skill that ships in the image is refused an edit and a delete, and the refusal says why.
  • A skill whose name collides with one that ships is refused, and the shipped skill is the one that keeps the name.
  • A skill saved without a name, without a description, without a body, or with a description over more than one line is refused and nothing is stored.
  • A skill written with files is a folder on disk, and one written without is a single file; whichever form it had before is gone, and a skill that is a folder is deleted whole.
  • A file whose path would leave the skill's folder, starts with a dot, is empty, repeats another's, or names SKILL.md is refused, and nothing is stored.
  • A save that leaves the files out keeps the ones the skill has.
  • The interface sets whether a skill is on by default, and the choice survives a reload.

Required skills

SkillTeaches
schedulingHow to turn a condition into a shell command, which is nearly always possible; when it genuinely is not; choosing expiry and interval.
keeping-recordsHow to keep whatever the operator asks to have remembered — a series that accumulates (measurements, appointments, incidents), a list with no dates, or a note of a fact, a preference, or a decision — as files in the session's working directory; that every date written comes from clock in the same turn; and how to read any of it back with a command.
researchingHow to answer a question from the web: plan narrow searches, read the page rather than the snippet, rank sources from primary to unverified, keep findings in a file as they accumulate, and give every claim its source.

Acceptance criteria

  • Every required skill ships, loads, and is on by default.
