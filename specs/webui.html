Web UI

One interface at every width. The phone keeps the conversation list behind a drawer; the laptop pins the same list open beside the same pane.

See the rendered mock.

Shell

Every screen is the same three parts: a rail of conversations and panels, a header naming where you are and what can be done here, and one pane between them. The width decides the shape of the rail and nothing else — there is no screen that exists at one size and not at another, and no list drawn twice. Below 900 pixels the rail is a drawer over the pane, opened from the header and closed by going anywhere; at or above it the rail is a column of the layout and the pane loses its back button, because the rail is the way back.

The rail links the panels used every day — Jobs, Tools, Skills — and More, which leads to the rest. Personas are chosen when a conversation starts and written rarely, so they are behind More.

Every screen has an address of its own, and reaching a screen changes it. A skill or persona being read or written is a screen, so the browser's back button leaves it for the list it was opened from. Saving or deleting leaves the same way: back to that list when it is behind the editor, and otherwise the list in the editor's place, so the history never holds a list twice.

A screen is drawn from requests that answer in their own time, so two screens opened one after the other can answer in the wrong order. The screen on the address bar is the one on the pane: a draw that is no longer the current one stops where it stands rather than painting its conversation, or a second composer, over the screen that replaced it.

A view's own actions — a conversation's jobs, files, summary, fork, details — belong to the header. They are one list rendered in two shapes: laid along the header where there is room for them, folded behind a single button where there is not. Which is on screen is the stylesheet's decision, so the two can never offer different things.

A transcript is held to a reading column whatever the screen; a list of jobs, tools, files, or skills takes the width the screen actually has, as a grid of cards rather than a strip down the middle.

Acceptance criteria

  • The conversation list is a rail beside the pane where there is room for one, and a drawer behind a single button where there is not — the same list either way, never two.
  • Opening the drawer, dismissing it, and going anywhere from it each leave exactly one thing on screen.
  • With the rail pinned open the pane offers no back button and the drawer no handle.
  • The rail names every conversation, newest activity first, marks the one being read, and carries its unread count. A conversation is kept or deleted; nothing sets one apart as archived.
  • The rail states the credit remaining and whether tools are sandboxed, without opening a screen to ask.
  • The page's first request on coming back is answered without waiting on OpenRouter; the credit shown is the last figure the agent heard, and the rail updates when a fresher one arrives.
  • The rail links Jobs, Tools, Skills, and More; personas are reached from More.
  • Opening a skill or persona, or starting a new one, changes the address, and the address alone opens it again.
  • An address naming a conversation that no longer exists opens a screen saying so, under a header of its own that offers nothing acting on another conversation; a screen whose answers are refused for any other reason says that instead of staying blank.
  • Saving or deleting a skill or persona returns to the list it was opened from without adding the list to the history a second time.
  • A screen still loading when another is opened paints nothing: the pane shows the conversation the address names, with one composer under it.
  • Whatever screen was left before its answers came back — a new conversation, a fork, a conversation's details, the More panel, a skill or persona — adds no section, button, or header action to the screen that replaced it.
  • A view's actions are one list, whether laid along the header or folded behind one button.
  • A transcript is held to a reading column; a list of jobs, tools, files, or skills takes the full width available.
  • Nothing in the interface is laid out at a fixed page width.
  • The interface follows the system's colour scheme, and is legible in both.
  • A request for reduced motion is honoured.
  • A control that is hidden is not on screen, whatever else the stylesheet says of it.

Installation

The interface is a progressive web app installed to the home screen. Installation is required rather than optional: an installed web app gets the full screen and its own icon.

Acceptance criteria

  • The app is installable to the home screen on iOS and Android.
  • It launches without browser chrome once installed.
  • Opening it while off the tailnet shows a clear connectivity message, not a browser error.
  • Every control is operable one-handed on a phone.

Conversation view

The primary screen. A transcript, an input, and a status line.

ElementShows
Prompt entryPersona, skills index, and full tool definitions, each collapsible with a token count. It sits at position zero and is the prompt for the session's whole life; nothing rewrites it and no section is editable.
MessagesUser and assistant turns, tool calls with their results. What the agent says is rendered markdown — headings, lists, tables, code blocks, links. What the operator typed is shown as they typed it.
EventsJob checks, forks, failures. A log line each — clock, kind, detail — quieter than messages and shaped unlike them. Only what nothing else records.
CompactionA banner standing where the agent's reading of the conversation begins, after the prompt. Says how many turns it replaced and the token count before and after, states that the agent reads the summary in place of everything before it, shows the summary, and offers to search what it folded away. The turns it kept word for word follow it, grouped and labelled as carried over; then what came since. What it covers is not drawn. Editable.
AttributionAny message produced by a job names the job and links to it.
Status lineWhile the agent is working, how long it has been working, counting, and the way to stop it. Model, context used against the compaction threshold, live cache size and its countdown, tokens per second while streaming, session cost.
RevertBeside each message that started a turn, a control that takes the conversation back to before it. It asks first, in a dialog that says what goes and what stays.
CopyA header action that puts the whole conversation on the clipboard as Markdown.
ComposerOne field, a way to attach a file, and a send. On a keyboard Enter sends and shift-Enter breaks the line; on a touch screen Enter breaks the line and the button is the send. On a keyboard the cursor is in it as soon as the conversation opens. Up and down step through what the operator has sent in this conversation, newest first, and back to what was being typed.

A conversation is drawn whole when it is opened, and grows from there: an entry that arrives is added after the last one, and a turn starting or ending changes only the row at the end that stands for the answer. Nothing already on screen is drawn again, so a tool result the reader opened stays open through the rest of the turn. An answer arriving is drawn at most once a frame, however fast its tokens come; the blocks of it that can no longer change are drawn once, and only the block still growing is drawn again. What it shows is exactly what the finished answer will show. A reader who has scrolled up is left where they are while it arrives; one at the end stays at the end.

A conversation that went somewhere unwanted is taken back from the message where it turned. Each message that started a turn — the operator's, or a job's wake — carries a revert control beside its time: the undo emoji, ↩️, in colour on a button with an edge of its own, so it is found when it is looked for. It asks before it acts, in a dialog that slides over the screen like every other: how many entries go, that the agent will no longer see them, that files it wrote and jobs it created stay, and, when one would be undone, that a compaction goes with them. Confirmed, the conversation is drawn again without what was taken back, ending at the line that records the revert, and the operator's message is back in the composer to be changed and sent. Nothing is erased: the history and search still reach what was taken back (Sessions).

The same conversation can be open on more than one device. Every entry goes to every page that is connected, whichever device wrote it, so a message typed on a laptop appears on a phone showing that conversation. A page that was not connected when something was written — a phone in the background, a laptop asleep — reads the rail and the conversation on screen again from the agent when its socket reconnects and whenever it is shown again. Shown again, it does this even if its socket still looks open, because a socket can survive a sleep without hearing anything; one that has closed reconnects at once rather than after its usual wait. Nothing is reloaded and the unread line stays where it was. What the page already holds is not fetched again: it asks only for the entries after the last one it has and adds those, so coming back to a long conversation costs what was written while it was away. A page holding a gap — an entry the socket dropped — reads the whole conversation instead. Opening a conversation asks for the session and its transcript at once rather than one after the other.

The agent sits behind a password the proxy in front of it asks for, and a browser forgets that password after a while. From then on every request is refused with a request for the password, and a phone asked for it by several requests at once can crash rather than ask. So a page shown again makes one request first, and only once that is answered does it reconnect and read the rail and the conversation. A socket that drops makes the same check before it opens again, rather than retrying blind. When the check is refused, the page reloads instead: the password is asked for once, by the page itself, as it was when the page was first opened. A check already under way is shared, not sent again.

Acceptance criteria

  • Assistant output streams token by token.
  • Tokens per second is shown during generation and the final figure remains after it completes.
  • Each answer names the provider that served the call producing it, beside what that call read from the cache (Architecture).
  • Context usage is shown against the session's compaction threshold, not the model's window.
  • The header's title and the status line's figures follow the conversation while it is open: the title its first answer gives it, and the cost and context each turn moves, show without opening it again.
  • The estimated cost of the next call is shown, and whether it will be cached: the prompt and the conversation as they would be sent now, at the model's prices, with what a live cache holds priced as a read.
  • An event is laid out as a log line — clock, kind, detail — with no speaker and no bubble, so it cannot be read as a message or a tool result.
  • A session identifier appearing in an event or a prompt section is a link to that session.
  • The session list is ordered by last activity, and can be reordered by disk used, largest first.
  • Each session row shows what it holds on disk and offers a delete that confirms first.
  • Copied messages in a fork are marked by their styling; where they came from is said once, in the seeding event, not on each one.
  • Colour marks a failure and nothing else; a routine tick that did not fire is not coloured.
  • Long transcripts scroll to the newest entry without loading the entire history.
  • A tool call can be expanded to show its arguments and result.
  • A collapsed tool result previews its first line, and a call that returned nothing says so, so an empty result is never mistaken for a missing one.
  • A collapsed tool call previews its arguments the same way, and a call made without arguments says so.
  • A failed tool call is expanded by default and marked as an error.
  • A tool call that wrote to standard error offers those logs behind a toggle of their own, closed by default — including on a call that failed, where the error is already open: the error is the answer and the logs are the evidence.
  • A tool call that wrote nothing to standard error offers no logs toggle, so a toggle never promises detail that is not there.
  • Scrolling to the top of any conversation reaches the prompt entry it opened with.
  • A message sent from one device appears in the same conversation open on another without a reload, including one sent while the other's socket was down or its page hidden.
  • A page shown again with its socket closed reconnects at once, and opens only one new socket.
  • A page shown again makes one request before any other, and reconnects and reads the conversation only once it is answered.
  • A page shown again, or a dropped socket retrying, whose password has lapsed makes that one request and reloads, opening no socket and asking for nothing else.
  • A compacted session shows the prompt, then the newest compaction's banner, then the turns it kept word for word, then what came since: the order the agent reads them in.
  • The entries a compaction covers, and every superseded compaction, are not drawn in the conversation at all, and nothing there offers to reveal them; the banner offers a search of this conversation instead.
  • A fork's seeding event, which says where it was copied from, is drawn after the prompt even when a compaction the fork carries covers its position: it is the fork's own record, not something the summary stands for.
  • The turns a compaction kept word for word are grouped after its banner under a label saying they were carried over, and how many turns they are.
  • The banner names itself a compaction, says the agent reads its summary in place of everything before it, and shows the turn count and the tokens before and after.
  • The compaction summary is editable, and an edit changes what the next turn sends.
  • A compaction says that it reset the cache.
  • The status line shows the live cache size and counts down to its expiry, and shows it as expired when it is.
  • A provider that caches on its own, without the agent's marker, reports no lifetime; its cache is shown as held by the provider, and no countdown is invented for it.
  • Each assistant message shows the cached proportion of the call that produced it, from what the provider reported, and says so plainly when there was no hit.
  • No cache lifetime is shown per message.
  • Expanding the tool section shows every tool definition as the model receives it.
  • Opening or closing a section of the prompt changes that section alone, in that conversation alone: nothing else is drawn again, and a tool result the reader opened stays open.
  • An assistant message renders its markdown: headings, bullet and numbered lists, tables, block quotes, rules, emphasis, inline code, and fenced code blocks that keep their lines.
  • A turn still streaming renders as markdown while it arrives, including a fenced block whose closing fence has not been sent yet.
  • A turn streams only in its own conversation: one left while its answer arrives leaves nothing of that answer, and no word that it is generating, in any conversation opened after.
  • A message the operator typed, and a wake carrying a job's stored prompt, are shown verbatim and are never rendered.
  • Markup in model output is shown as text and never becomes markup: a link renders only when it points at the web, an address, or this app, and an image renders as a link rather than a fetch.
  • Any character model output holds is drawn as text, a NUL included, which is shown as a replacement character: nothing in an answer can stop the conversation drawing.
  • A keyboard sends the composer with Enter and breaks the line with shift-Enter; a touch screen breaks the line with Enter and sends from the button. The platform's own combination sends on either.
  • A key that ends a composition — an accent, a kana, a candidate — sends nothing.
  • Opening a conversation on a keyboard puts the cursor in the composer without scrolling the transcript; on a touch screen nothing is focused, so no keyboard rises.
  • Up in the composer recalls the operator's own messages in this conversation, newest first, and never a job's prompt; down steps back to the newest and then to what was being typed. Up reaches history only from the first line and down only from the last, and with a modifier held the arrows only select.
  • From the moment a message is sent until the agent's last queued turn in that conversation ends, the status line says the agent is working and counts the seconds; a conversation opened mid-turn counts from when the turn started, and the indicator goes when the turn ends.
  • A session reports whether it is working and for how long, and the change is pushed as it happens, once when work starts and once when the last queued turn ends.
  • While a conversation is working, the status line offers a way to stop the turn, and the offer goes when the turn does.
  • While a conversation is working and nothing of the answer has arrived yet, the transcript shows the agent thinking where the answer will appear; the first word of the answer replaces it, and it goes when the turn ends.
  • When a turn ends, the conversation scrolls to its answer, even if the reader had scrolled away while it worked.
  • An entry arriving is added without drawing again what is already on screen; a tool result the reader opened stays open.
  • A conversation opened while it is working shows every entry, each once: what the socket delivers while the transcript is on its way is kept beside it, and an entry heard twice is drawn once.
  • An answer arriving reads exactly as the finished answer will, is drawn at most once a frame, and draws again only the block still growing; a reader who has scrolled up is left where they are.
  • The whole conversation copies to the clipboard as Markdown from its header: the title, every message with its speaker and time, each tool call with its arguments, each tool result clipped to a readable length that says how much it left out, the logs of any call that wrote some, and each compaction's summary — and not the prompt or the event log.
  • Every message that started a turn, the operator's or a wake's, offers to revert the conversation to before it; no other entry does.
  • Reverting asks first, in a dialog: it says how many entries go, that the agent will no longer see them, that files the agent wrote and jobs it created are not undone, and, when it would, that a compaction is undone with them. Dismissing it changes nothing.
  • While the conversation is working the revert dialog says to stop the turn first, and offers no revert.
  • A revert the agent refuses says why, and changes nothing on screen.
  • After a revert the conversation is drawn without what it took back, on every page showing it, and ends with the line recording the revert. The operator's message is in the composer, ready to change and send, unless something was already being typed there, which is kept; a wake puts nothing there.
  • Entries a revert took back are not drawn in the conversation and are not copied with it; the history shows them dimmed, and a search hit on one says the agent no longer sees it.

Session management

Every page reads the session list whenever a count on it moves, so the list is built to be cheap to read. Two of its figures are costly to measure — the context each conversation would send, and what its working directory holds — and both are kept between reads for exactly as long as what they measure cannot have changed. The context figure is kept until the transcript grows. What a directory holds is measured again after anything the agent does or sees touches it — a tool call, a check, an upload, a delete — and is never more than a minute old, which covers a process a command left running that goes on writing. A single session asked about on its own, as the files screen asks, is always measured on the spot.

Acceptance criteria

  • All sessions are listed, newest activity first, with title, model, and unread count.
  • A session can be created, renamed, and deleted.
  • Search finds text across all sessions and opens a result at its position.
  • Search opened from a conversation looks in that conversation, and can be widened to every conversation in one tap. It searches as it is typed, each word matching as a prefix, and punctuation is looked for rather than read as syntax.
  • Each search hit says who wrote it and when, marks what matched, and says so when the agent no longer sees it.
  • A search hit opens the conversation's history at that entry: everything the session stored, oldest first, folded entries, superseded summaries, and what a revert took back included and dimmed, the hit picked out and scrolled to. Nothing in the history can be edited or sent.
  • The list shows which sessions have jobs attached.
  • Every session shows what it occupies on disk, so it is clear what deleting one frees.
  • What a tool writes or an upload adds, and what a delete frees, shows in the session list on its next read; a session's context figure moves with every entry.
  • A session can be forked in one action.
  • A fork links back to its origin, and the origin links forward to it.
  • A session can be compacted on request, from the session itself, without waiting for the threshold, from its header.
  • A requested compaction that is refused says why.
  • A conversation can be put to several models at once, with the models and the message chosen on one screen that says what asking that many models costs.
  • The candidates of a comparison are shown together, each headed by its model, each filling in as it answers.
  • A candidate still working with nothing of its answer yet shows it is thinking, in its own column; when it finishes, its column scrolls to the answer, and a redraw leaves every other column where its reader left it.
  • Keeping a candidate is one action from that screen, confirmed, and the confirmation says the other candidates will be deleted.
  • Asking is one action: the button stops offering once a comparison is under way, so a second press cannot start a second comparison of the same question.
  • An undecided comparison is reachable again after leaving its screen — from any candidate's header, from the mark on its row in the list, and from the origin's record of it.
  • Every compaction a session has had is reachable from it, newest in force.

Per-session details

Acceptance criteria

  • The details screen states the session's model, tools, skills, grants, and persona, and states them as read: nothing on it changes any of them, and it says that a different configuration is reached by forking.
  • The details screen offers only what a conversation can still be given or denied once it exists: a new title, when it compacts, and deletion. It does not repeat an action the conversation's header already carries.
  • The details screen sets the size at which this conversation compacts and how much it keeps word for word, says the second can be at most half the first, and says why when a pair is refused (ADR-060).
  • The details screen renames the conversation in place, because nothing in the prompt reads the title. A blank is not a rename.
  • The persona is chosen from the personas on disk, the built-in one among them, and the screen says that choosing one replaces the built-in persona entirely.
  • The model is chosen in a dialog that slides over the screen. Each model in it shows its price per million input and output tokens, its context window, and its intelligence, coding, and agentic indices where the gateway reports them, and links to its page on OpenRouter. An index the gateway did not report is absent, never zero.
  • A model's figures — prices, context, indices — are one wrapping row of small figures under its name, wherever a model is named: never a card each.
  • Wherever a screen names a model, its figures come from the catalogue as the agent currently holds it, fetched when the screen is drawn, so the configuration and the model dialog never show one model at two prices.
  • The model dialog ranks by intelligence by default, and can be ranked by price, context, or release instead; a model without the figure ranked on comes last.
  • The model list is searchable: a query narrows it to the models whose identifier or name contains every term, and the model already chosen stays selectable even when the query excludes it.
  • Dismissing a dialog changes nothing; only picking in it does.
  • The granted environment is chosen in a dialog listing every variable name the agent could grant, those from .env first, each with a checkbox (ADR-048). No value is shown, the model key is not listed, and a granted name that is no longer set is still listed and can be unticked.
  • A skill that ships off starts unticked in a configuration that did not choose its skills, and ticking it chooses them.
  • Forking opens a configuration screen carrying the origin's settings, and creates the fork when it is confirmed.
  • The fork screen says that the whole conversation is copied and that the origin keeps its jobs.
  • Starting a conversation reaches the same screen, prefilled with the most recent session's tools, skills, and grants, on the model last chosen (ADR-049).
  • Starting a conversation and creating a fork are each one action: the button stops offering while its request is out, so a press that lands twice creates one, and a refusal says why and offers it again.
  • No screen offers to edit the configuration of a session that already exists.
  • Enable-all and disable-all act on the whole list in one tap.

Files

Every conversation has a files screen: what its working directory holds, what to add to it, and the archive of the whole session. The directory is drawn as the tree it is — a cloned repository, an unpacked archive — with directories first and each one folding in a tap. A tree of more than a hundred entries opens folded, so one large directory does not bury everything beside it.

A file is also attached from the composer. It uploads the moment it is picked and waits above the message as a chip that shows its progress, until the message is sent. An upload writes nothing into the conversation, so the message names the files it carries, and that line is how the agent learns they are there.

Acceptance criteria

  • A file can be uploaded from a phone, including from the camera and the photo library.
  • An uploaded file is written to the session's working directory and appears in its file list.
  • An upload never replaces a file already there: a name already taken gets a number — image.jpg, then image-2.jpg — and the message names each file where it landed. Two photos from a phone's camera, both called image.jpg, are two files.
  • The file list shows every file and directory the session holds as a tree, empty directories included. A file shows its size and age and can be downloaded or deleted; a directory shows what it holds and folds and unfolds when tapped.
  • A tree of more than a hundred entries opens with its directories folded; a smaller one opens in full.
  • A file attached from the composer shows as a chip with its upload progress, and stays until the message is sent or it is taken off.
  • A message sent with attachments names each one, as a path in the working directory; a message may be only its attachments.
  • A message is not sent while one of its files is still uploading or has failed to.
  • The files screen states what the session occupies on disk, split between its files and its transcript.
  • Images are passed to models that accept them; other files are made available to the agent's file tools.
  • Upload progress is shown and a failed upload can be retried: in the composer, by tapping its chip.
  • Files larger than 250 MB are refused before transfer begins.
  • Uploads are deleted with the session that holds them.
  • A session is exported to a zip from its files screen, and an archive is imported from the session list.

Assets

The interface is served from disk, and its scripts carry no version in their URLs. Every asset is therefore sent with Cache-Control: no-cache: the browser may keep a copy but must ask before reusing it. Without that, a cached script runs against markup it no longer matches, and the failure looks like a bug in the page rather than a stale copy of it.

Whatever a browser accepts compressed is sent gzipped: the interface's scripts and stylesheet, and every JSON answer, of which a transcript carrying its tool results is the largest. They shrink five to ten times, and nothing in front of the agent can be relied on to do it. A file from a session's directory and an exported archive go out exactly as stored: either may be compressed already, and a range of a file has to mean the file's own bytes.

Acceptance criteria

  • Every interface asset is served with Cache-Control: no-cache.
  • An unchanged asset revalidates to 304 rather than being sent again.
  • Assets and JSON answers are sent gzipped to a browser that accepts it; a session's files and archives are sent as stored.

Unread work

The agent cannot interrupt the operator. It has no notification tool and no way to reach a device — that is ADR-026 and it still holds. What the interface may do is tell the operator about output they have not read, and it does that in two places.

The first is a count. The session list shows unread assistant messages per session, each job carries its own run log, and a tripped breaker is a banner across the top of every screen.

The count is not kept, it is derived. Each session records the last entry the operator was shown, and what is unread is the assistant messages after it — whoever started the turn, the operator or a job. A read names the entry it read through, so a message that arrives between the page loading and the read reaching the agent stays unread, and a read point only ever moves forward. A conversation is read when it is opened, and a message arriving in the conversation on screen is read as it arrives, unless the page is hidden; then it is read when the page is shown again. A read says whether it cleared anything. The rail redraws after one that did of its own accord, and whenever its socket connects, rather than waiting to hear the list moved, so a phone back from the background does not keep a count it has already cleared. Most of what arrives on screen is a tool call or its result, and reading past it clears nothing; such a read changes nothing a list shows, so neither the page nor the agent sends anyone back for the session list, which is the costliest thing the agent serves.

A conversation with unread messages opens at the first entry after the read point, under a line that marks it, rather than at its end with what was missed above the fold. The line stays where it is while the conversation is open.

The second is a system notification, on the narrow terms of ADR-027: while a tab is open, a new agent message the operator is not currently reading shows a banner. It is the browser's own notification API and nothing else — no push service, no service worker, no keys, no subscription — so it reaches a running browser and nothing else. A closed browser learns nothing, and this is stated rather than implied.

The conversation is the title and its newest line is the body, clipped: a banner is a pointer to the transcript, not a copy of it. One banner per conversation, replaced as the exchange continues. Opening it goes to that session.

Permission is the operator's, asked for once from the settings screen, and the screen states what this device will actually do — on, off, blocked for the site, or an origin without the API at all. Where permission is absent the count is the whole of the signal; the interface never opens a popup of its own instead.

Acceptance criteria

  • A new assistant message in a session the operator is not reading shows a system notification, whether the page is hidden or showing another screen.
  • A message in the conversation on screen shows no notification.
  • A user message, a tool result, an event, and a turn that only called tools show no notification.
  • The messages a fork copies show no notification and reach no page one by one: the copy is written at once, and pages hear only that the list moved.
  • Successive messages in one session replace each other rather than stacking.
  • Opening a notification goes to the session that produced it.
  • Without permission nothing is shown at all — no banner and no in-app popup — and the settings screen says so.
  • The system makes no outbound connection to any push service, and nothing reaches a closed browser.
  • The session list shows the unread assistant message count for each session, and clears it when the session is read.
  • A message a job's wake produced counts as unread exactly as a reply to a typed message does.
  • A read clears only what it names: a message written after the point read through stays unread, and a late read for an earlier point does not make anything unread again.
  • Opening a conversation clears its count on the rail without waiting for the socket, and the rail refreshes whenever the socket connects.
  • A page catching up fetches only the entries written after the last one it holds and adds only those; with nothing new, nothing on screen changes.
  • A read that clears no count sends no page, on this device or another, to read the session list again.
  • A message arriving in the conversation on screen is read at once; while the page is hidden it stays unread until the page is shown.
  • A conversation with unread messages opens scrolled to a line marking the first of them; one with none opens at its end.
  • A fork starts with nothing unread.
  • A job that failed shows it in its own log, and a tripped breaker appears as a banner, without either interrupting.

Status and cost

Acceptance criteria

  • Remaining OpenRouter credit and usage are displayed and refreshed at least hourly.
  • Per-session cost is shown and derives from reported token usage and current model prices.
  • Cache hit rate is shown for sessions with jobs attached.
  • A tripped circuit breaker is visible from the session list without opening a session.

Panels

Jobs, tools, skills, and personas each have a management panel. Tools that ship their own panel appear alongside them. More also leads to Metrics.

Skills and personas are the same kind of thing on disk — a Markdown file with frontmatter that the operator writes — so they are listed, written, and deleted through one screen, and only the wording differs.

Acceptance criteria

  • Every job, tool, skill, and persona is viewable without the agent.
  • A skill or persona the operator wrote is created, edited, and deleted in the interface, with its name, its one-line description, and its body.
  • One that ships in the image is shown read-only, and says so rather than offering an edit that would fail.
  • A save that is refused says why and leaves what is on disk unchanged.
  • A new skill or persona under a name already taken is refused, and the one of that name is kept: a document is changed by opening it, never by writing a new one over it.
  • A job's run log is readable from the job, without opening the conversation it fires into.
  • The jobs panel offers to delete the finished jobs it is showing, only while it is showing some, saying how many and asking first; a scheduled job is never among them.
  • A job is shown as its own settings, not as a category the interface worked out for it.
  • Panels contributed by tools are listed with built-in panels and are visually consistent with them.
  • The Tools panel shows, for each tool, the paths it may read and write and the ports it may connect to, from the policy the sandbox applies, and that it can never reach the operator's port; it sets what that tool's manifest asked for apart from what every tool gets; it says when either half is not enforced, and that a builtin runs inside the agent.

Metrics

How much each skill, tool, and job is used, on one screen behind More. Without it the question was answered by copying every transcript off the server and counting by hand, which is also the one thing a conversation about health records should never need.

The numbers are counted, on the way out, from what the agent already stores: the transcripts and each job's log (ADR-065). Nothing is recorded for them, so nothing can disagree with the transcript, and what a deleted conversation did leaves with it. What a fork copied from its origin happened once and is counted once, in the origin.

  • Skills. A read is a skill_read call for that skill that succeeded. Beside it, how many conversations read it out of how many were offered it: a conversation is offered a skill when the index its model was shown listed it, which is read from the conversation's own prompt rather than from the skills loaded now, because a prompt is fixed for a conversation's life. A skill read in few of the conversations offered it is one whose description is not doing its job.
  • Tools. Calls, failures (a result that says it did not succeed), how many conversations called it, and what its newest failure said, which is usually enough to tell a broken tool from one the model calls wrongly.
  • Jobs. Each job's wakes by outcome — acted, skipped, failed — from its log, and what the model calls of its wakes cost, from the transcript. A check costs nothing and adds nothing to the cost.

Every tool and skill loaded is listed whether or not it was used, since one nobody uses is an answer too, and one that is no longer loaded keeps the uses it had, marked so. A job is listed when it woke in the window or is still scheduled. "In how many conversations" is out of the conversations that had a model call in the window; one that was created and never spoken in showed its model nothing.

Each of the three is a table: one row per skill, tool, or job, its figures in columns of their own, right-aligned, so a column is read down and a row across without reading a sentence for each. A name too long for the row is cut short rather than wrapped, except a job's prompt, which is how a job is recognised and gets two lines first. A tool's newest failure is the one thing too long for a column, and is a line of its own beneath that tool's row. A row nothing used is dimmed. The conversations a skill was read in are written as a count out of those offered it, as in 1/4, and the screen says once what that means.

The window is the last 7 days, the last 30, or everything stored; 30 is the default. It is in the address, so going back returns to the window that was being read.

Acceptance criteria

  • The More panel leads to a Metrics screen.
  • Skills, tools, and jobs are each a table with one row per item and a column per figure; a tool's newest failure is a line beneath its row.
  • Each skill says how often it was read, and in how many of the conversations offered it; one never read says so.
  • Each tool says how often it was called, how often that failed, and what its newest failure said.
  • Each job says how many of its wakes acted, were skipped, and failed, and what its wakes cost, and its prompt opens the conversation it fires into.
  • Every loaded tool and skill is listed whether or not it was used; one no longer loaded keeps its uses and is marked not loaded.
  • What a fork carried over from its origin is counted once.
  • A deleted conversation's uses are no longer counted.
  • A window of the last 7 or 30 days counts only what happened in it; the window chosen is kept in the address.

Version and changelog

The interface says which build it is. The version is the commit the image was built from — the same string the image is tagged with, so what is on screen is what a rollback names. The image carries no git history, so the commit and the build time are stamped into the binary at build time; a binary built without that stamp says dev rather than inventing a number.

What changed is a file, CHANGELOG.md, written by whoever made the change and shipped with the app. It is rendered as markdown, newest first, and the interface reads it rather than deriving it: the container has no repository to ask.

The screen is served the dated entries and nothing above them. A changelog opens with a note to whoever writes it — how the file is organised, and that a change to behaviour belongs in it in the same commit — and that is a rule for working in the repository, not something to read on a phone after an upgrade. The rule lives in CLAUDE.md; the file keeps only what it is for.

Both sit at the foot of the More panel, under the device and isolation sections. Nothing about a version is urgent — it is read once after an upgrade and never again — so the changelog stays folded until it is asked for, and neither is ever shown over a conversation.

Acceptance criteria

  • The interface names the version it is running and when that build was made, from the More panel, without interrupting anything.
  • The version is the commit the running image was built from; a build with no stamp says so rather than showing a number it invented.
  • The changelog ships with the app, is read from disk rather than derived from a repository, and is rendered as markdown newest first.
  • The changelog is folded away until it is opened.
  • The changelog reaches the screen from its first dated section on, so a note addressed to whoever writes the file is never shown to whoever reads it.
  • A missing changelog file leaves the version readable and says the changelog is unavailable.
